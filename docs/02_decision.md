## D-001. 기술 스택: Python + FastAPI

| 항목 | 내용 |
|------|------|
| **결정일** | 2026-08-06 |
| **상태** | 확정 |

### 결정

백엔드는 **Python + FastAPI**로 구현한다. vCenter는 pyVmomi, Hyper-V는 pypsrp/WinRM(PowerShell Remoting) + WMI로 연동한다.

### 근거

- 동일 조직의 collectorinfra 프로젝트와 스택이 일치하여 인프라·운영 노하우와 Claude Code 구성요소를 재사용할 수 있음
- pyVmomi는 VMware가 관리하는 공식 Python SDK로, 대규모 인벤토리 수집에 필요한 PropertyCollector API를 완전히 지원함
- Hyper-V는 네이티브 관리 인터페이스가 PowerShell/WMI이며, pypsrp로 원격 실행이 가능함
- `scripts/arch_check.py`(Python AST 기반 규칙 검사)를 재사용 가능

### 고려한 대안

| 대안 | 장점 | 채택하지 않은 이유 |
|------|------|-------------------|
| C# / ASP.NET Core | Hyper-V/WMI 네이티브 접근, Windows 환경 친화 | 조직 내 기존 스택과 불일치, 아키텍처 검사 도구 재작성 필요 |
| Node.js / TypeScript | 프론트엔드와 언어 통일 | vCenter/Hyper-V용 성숙한 라이브러리 부족 |

## D-002. 아키텍처: Clean Architecture 8계층

| 항목 | 내용 |
|------|------|
| **결정일** | 2026-08-06 |
| **상태** | 확정 (2026-08-06 읽기 전용 범위 확정에 따라 모듈 구성 갱신) |

### 결정

의존성 방향을 안쪽 → 바깥쪽으로 강제하는 8계층 구조를 채택하고, `scripts/arch_check.py`로 자동 검사한다.

```
domain → config/utils → infrastructure → application → orchestration → interface → entry
```

| 계층 | 경로 | 책임 |
|------|------|------|
| domain | `src/domain/` | 자원 엔티티, 연결 정보, 메타데이터, 변경 이력, 권한 모델, 포트(Protocol) |
| config | `src/config.py` | 설정 |
| utils | `src/utils/` | 공유 유틸 |
| infrastructure | `src/infrastructure/` | 하이퍼바이저 수집 어댑터, DB, 캐시, 보안, 저장소 |
| application | `src/application/` | 유스케이스 (조회·검색, 정규화, 메타데이터 관리, 변경 이력, 리포트) |
| orchestration | `src/orchestration/` | 수집 스케줄러/워커 |
| interface | `src/api/` | FastAPI 어댑터 |
| entry | `src/main.py` | 진입점 |

### 근거

- 하이퍼바이저 연동 코드(외부 의존이 크고 변경이 잦음)를 도메인 로직에서 분리하여 교체 가능하게 유지
- 계층 위반을 사람이 리뷰로 잡는 대신 스크립트로 자동 검출 (collectorinfra에서 효과 검증됨)
- **수집 워커를 `orchestration`으로 분리**하여 API 프로세스와 독립 배포 가능. 수집 부하가 조회 응답에 영향을 주지 않는다 (`spec.md` NFR-107)

### 고려한 대안

collectorinfra의 원본 계층에는 LangGraph 전용 계층(`prompts`, `nodes`)이 있었으나 이 프로젝트에는 LLM 파이프라인이 없어 제거했다.

## D-003. 하이퍼바이저 추상화: Protocol 기반 어댑터 패턴

| 항목 | 내용 |
|------|------|
| **결정일** | 2026-08-06 |
| **상태** | 확정 (2026-08-06 Protocol 명칭을 읽기 전용 성격에 맞게 변경) |

### 결정

`src/domain/ports.py`에 **`HypervisorInventoryReader`** Protocol을 정의하고, vCenter/Hyper-V 어댑터가 이를 구현한다.
유스케이스와 수집 워커는 Protocol만 알고, 구체 어댑터는 `interface`/`entry` 계층의 팩토리에서 주입한다.

Protocol 이름에 `Reader`를 명시한 것은 이 포탈이 읽기 전용임을 인터페이스 이름 자체로 드러내기 위함이다 (D-005 참조).

이를 강제하기 위해 `scripts/arch_check.py`에 특화 규칙을 구현했다:

1. `application`/`orchestration` → `src.infrastructure.vcenter|hyperv` **직접 import 금지** (error)
2. 하이퍼바이저 어댑터 간 **교차 참조 금지** (`vcenter` ↔ `hyperv`) (error)

### 근거

- 유스케이스에 `if hypervisor == "vcenter"` 분기가 퍼지면 하이퍼바이저 추가 시 전 계층을 수정해야 함
- 어댑터 간 교차 참조를 허용하면 두 구현이 묶여 개별 교체·제거가 불가능해짐
- 두 어댑터가 동일 Protocol 계약을 만족하므로 **동일 테스트 스위트로 계약 테스트**가 가능
- 향후 하이퍼바이저 추가(Proxmox, Nutanix 등) 시 어댑터 구현만으로 지원 가능 (`spec.md` NFR-106)

### 미결 사항 (결정 필요)

- vCenter ↔ Hyper-V 자원 모델 정규화 매핑 규칙 (Cluster ↔ Failover Cluster, Datastore ↔ CSV/SMB, 포트그룹 ↔ 가상 스위치) → `plans/02-domain-model.md`에서 설계 후 D-008로 기록
- ~~한쪽만 수집 가능한 속성(ResourcePool, vSphere Tags 등)의 Protocol 표현 방식~~ → **해소**: `ReaderCapabilities`로 표현 (`plans/03` §3). vSphere Tags는 양쪽 모두 미지원으로 확정 (**D-010**)

## D-004. 개발 방식: 멀티 에이전트 빌드 시스템

| 항목 | 내용 |
|------|------|
| **결정일** | 2026-08-06 |
| **상태** | 확정 (2026-08-06 Wave 구성을 읽기 전용 범위에 맞게 갱신) |

### 결정

collectorinfra 프로젝트의 Claude Code 멀티 에이전트 구성(team-lead + 4개 서브에이전트)을 이 프로젝트에 이관하여 사용한다.
품질 게이트는 `arch-check` → `/security-review` → `/code-review` → `/simplify` 순으로 적용한다.

Wave 구성:

| Wave | 병렬 모듈 |
|---|---|
| 1 | domain(모델·Protocol) ∥ security(자격증명) ∥ persistence(저장소) |
| 2 | vcenter 어댑터 ∥ hyperv 어댑터 ∥ auth |
| 3 | 조회·검색 유스케이스 ∥ 수집 스케줄러 ∥ 변경 이력 |
| 4 | API ∥ 포탈 UI ∥ 리포트·내보내기 |

### 근거

- Wave별 병렬 구현 + worktree 격리로 독립 모듈을 동시에 개발 가능
- 특히 **vCenter/Hyper-V 어댑터는 교차 참조가 금지되어 있어 병렬 구현에 구조적으로 적합**
- 자격증명 보호와 조회 범위 격리가 핵심 위험이므로 `/security-review`를 필수 게이트로 승격

### 원본(collectorinfra) 대비 변경 사항

| 항목 | collectorinfra | 이 프로젝트 |
|------|---------------|------------|
| 핵심 보안 제약 | 읽기 전용 DB (DML/DDL 차단) | 하이퍼바이저 쓰기 API 차단 + 자격증명 보호 + 조회 범위 격리 |
| 필수 품질 게이트 | arch-check, code-review | arch-check(읽기 전용 검사 포함), **security-review**, code-review |
| Wave 구성 | state/db/security → nodes → graph | domain → 수집 어댑터 → 유스케이스/워커 → API/UI |
| 스킬 카탈로그 | mcp-builder, frontend-design 등 | 현재 환경에 설치된 스킬만 (`plans/00-claude-skills-plugins.md` 참조) |

## D-005. 범위: 읽기 전용 인벤토리 포탈 + 코드 수준 강제

| 항목 | 내용 |
|------|------|
| **결정일** | 2026-08-06 |
| **상태** | 확정 |

### 결정

이 포탈은 **자원 정보를 수집·조회하는 읽기 전용 시스템**이며, 자원 생성·변경·삭제 기능을 구현하지 않는다.
프로비저닝, 전원 제어, 스냅샷 조작, 리소스 변경, 마이그레이션은 **명시적 비목표**다.

이를 문서 약속에 그치지 않게 하기 위해 **세 겹으로 강제**한다:

1. **권한 차단** — 하이퍼바이저 접속 계정에 읽기 권한만 부여 (vCenter: Read-Only 역할)
2. **인터페이스 차단** — 커넥터 Protocol에 조회 메서드만 정의 (`HypervisorInventoryReader`)
3. **자동 검사** — `scripts/arch_check.py`가 `src/domain/ports.py`와 하이퍼바이저 어댑터의 public 메서드명을 AST로 검사하여, 자원 변경 접두사(`create_`, `delete_`, `power_`, `migrate_` 등) 사용 시 error로 차단

세션·수집 제어 목적의 메서드(`start_session`, `stop_collection` 등)는 허용 목록으로 예외 처리한다.

### 근거

- 사용자가 요건 확정 시 "자원 생성이나 변경 기능은 필요하지 않다"고 명시
- 읽기 전용은 **보안 경계이자 운영 안전장치**다. 통합 포탈이 다수 vCenter/Hyper-V에 대한 쓰기 권한을 갖는 것은 그 자체가 조직 전체의 단일 침해 지점이 된다
- collectorinfra 프로젝트에서 "읽기 전용 DB 접근"을 코드 수준에서 강제한 방식이 효과적이었으며, 동일 패턴을 적용
- 개발 중 편의를 위해 제어 메서드를 슬쩍 추가하는 것이 가장 흔한 범위 이탈 경로이므로, 리뷰가 아닌 자동 검사로 막는다

### 한계 (인지하고 있어야 할 것)

메서드명 검사는 **어댑터 구현 내부의 실제 쓰기 API 호출까지 잡지 못한다.**
예를 들어 `get_vm_status()` 안에서 pyVmomi의 `PowerOffVM_Task()`를 호출하면 검사를 통과한다.
따라서 verifier는 어댑터 구현체의 **실제 호출 대상 API를 코드에서 직접 확인**해야 한다 (`.claude/agents/verifier.md` 검증 항목 1번).

### 고려한 대안

| 대안 | 채택하지 않은 이유 |
|------|-------------------|
| 문서에만 명시 | 개발 중 범위 이탈을 막지 못함 |
| 런타임 차단 (호출 시점 검사) | 이미 코드에 존재하는 것을 실행 시점에 막는 것이라 늦음. 정적 검사가 우선 |
| 읽기 전용 계정에만 의존 | 계정 권한 설정은 운영 환경에서 바뀔 수 있음. 코드 차원의 방어가 필요 |

## D-006. 데이터 정합성: CI 식별 규칙과 속성 출처 우선순위

| 항목 | 내용 |
|------|------|
| **결정일** | 2026-08-06 |
| **상태** | 확정 (세부 규칙은 `plans/02-domain-model.md`에서 상세화) |

### 결정

ITIL CMDB의 식별·조정(Identification & Reconciliation) 개념을 도입한다.

**CI 식별 규칙** — 재수집 시 동일 자원을 식별하는 속성 우선순위 (VM 기준):
1. 연결 ID + 하이퍼바이저 고유 ID (vCenter `instanceUuid` / Hyper-V VM GUID)
2. BIOS UUID
3. MAC 주소 + 이름

식별된 자원은 **갱신**하고, 식별되지 않을 때만 신규 생성한다. 중복 레코드 생성은 결함으로 취급한다.

**전제 — 연결 ID 불변성**: 1순위 키에 연결 ID가 들어가므로, 연결 ID는 포탈이 생성한 UUID이며
주소·계정·표시명을 수정해도 **절대 바뀌지 않는다** (`spec.md` FR-110).
vCenter 서버 이전이나 IP→FQDN 변경 시 연결을 새로 등록하면 1순위 키가 바뀌어 해당 하이퍼바이저의
**모든 자원이 중복 생성**되므로, 기존 연결을 수정하는 경로만 제공한다.

**속성 출처 우선순위(조정 규칙)** — 동일 속성을 여러 경로로 얻을 때의 신뢰 순서:
- 게스트 OS: 도구 감지값(`guest.guestFullName` / KVP `OSName`) > VM 구성값(`config.guestFullName`)
- **포탈 입력 메타데이터(소유자·환경·용도 등)는 수집 데이터가 덮어쓰지 않는다**

**수집 불가 표현** — VMware Tools·통합 서비스 미설치로 게스트 정보를 얻지 못한 경우
`None`(값 없음)이 아니라 **사유를 포함한 "수집 불가" 상태**로 표현한다.

### 근거

- CMDB는 중복 CI를 만들지 않고 기존 레코드를 갱신해야 하며, 사용 중지된 CI를 방치하면 stale 데이터가 서비스 맵을 오염시킨다는 것이 ITIL CMDB의 기본 원칙
- 다수 수집 소스가 같은 속성을 갱신할 때 신뢰 순위를 정하지 않으면 값이 왕복하며 불안정해짐 (ServiceNow I&R의 reconciliation rule과 동일 문제)
- 게스트 IP·OS는 도구 의존이라 100% 수집이 불가능한데(`spec.md` CST-02), 이를 빈 값으로 두면 "IP가 없는 VM"과 "IP를 알 수 없는 VM"이 구분되지 않아 인벤토리 신뢰도가 무너진다

### 미결 사항

- 삭제 자원의 유예 기간 (미발견 → 폐기 전환까지)
- 변경 이력 보존 기간 및 아카이브 정책
- 동일 자원이 서로 다른 연결에서 중복 수집될 때의 처리 (`spec.md` FR-308)

## D-007. 수집 방식: 조회·수집 경로 분리

| 항목 | 내용 |
|------|------|
| **결정일** | 2026-08-06 |
| **상태** | 확정 |

### 결정

사용자 조회 요청은 **하이퍼바이저를 직접 호출하지 않는다.**
수집 워커가 주기적으로 인벤토리를 수집하여 저장소에 저장하고, 조회는 저장소만 참조한다.

vCenter 수집은 **PropertyCollector + ContainerView + RetrievePropertiesEx 페이징**으로 필요한 속성만 일괄 조회한다.
자원을 하나씩 순회하며 개별 속성을 읽는 방식은 금지한다.

> PropertyCollector는 SOAP(vim25) 전용 메커니즘이다. 이 제약이 vCenter 접근 방식 선택을 규정한다 → **D-010**.

### 근거

- 조회 응답 목표(1초 이내, `spec.md` NFR-101)를 하이퍼바이저 실시간 호출로는 달성할 수 없음
- 다수의 사용자 조회가 그대로 vCenter API 호출로 전달되면 하이퍼바이저에 부하를 주며, 이는 운영 시스템에 대한 위험임
- 하이퍼바이저 장애 시에도 조회가 동작해야 함 (부분 실패 허용, NFR-301)
- PropertyCollector는 VMware가 대규모 환경의 일괄 조회를 위해 제공하는 표준 메커니즘이며, 개별 속성 순회 대비 왕복 횟수를 크게 줄인다

### 트레이드오프

조회 데이터는 **마지막 수집 시점의 스냅샷**이므로 실시간이 아니다.
이를 사용자가 오해하지 않도록 자원별 최종 수집 시각과 신선도를 UI에 표시한다 (`spec.md` FR-502).
실시간성이 필요한 요구(성능 모니터링, 알람)는 이 프로젝트의 범위가 아니다 (`spec.md` §1.2).

## D-008. 연결 자격증명 관리와 인증 실패 처리

| 항목 | 내용 |
|------|------|
| **결정일** | 2026-08-06 |
| **상태** | 확정 (암호화 키 관리 방식은 미결) |

### 결정

하이퍼바이저 접속 정보는 관리자가 포탈 화면에서 직접 입력하며, 다음 규칙을 따른다.

1. **연결 유형별 입력 폼 분기** — vCenter와 Hyper-V는 입력 항목이 다르다.
   특히 Hyper-V는 **WinRM 인증 방식(NTLM / Kerberos / CredSSP)과 프로토콜(HTTP/HTTPS)** 선택이 필요하다.
2. **비밀번호 수정 규약** — 수정 화면에서 기존 비밀번호는 표시하지 않고, 입력란을 비워두면 기존 값을 유지한다.
3. **인증 실패 시 자동 재시도 중단** — 실패 원인을 인증 실패와 네트워크·서버 오류로 구분하고,
   인증 실패면 재시도하지 않고 연결을 "자격증명 오류" 상태로 전환한다. 관리자가 자격증명을 갱신해야 재개한다.
4. **중복 등록 차단** — 동일 주소+계정 조합의 연결은 등록을 막는다.
5. **연결 삭제 시 자원 보존(권장안)** — 수집된 자원을 즉시 삭제하지 않고 "연결 해제됨" 상태로 보존한다.

### 근거

- **3번이 가장 중요하다.** 하이퍼바이저 접속 계정은 대개 AD 통합 서비스 계정이며,
  잘못된 비밀번호로 수집 워커가 주기마다 재시도하면 **계정 잠금 정책에 걸려 계정이 잠긴다.**
  그 계정이 백업·모니터링 등 다른 시스템에서도 쓰이면 인벤토리 포탈 하나 때문에 연쇄 장애가 발생한다.
  일반적인 재시도 로직(NFR-304, 최대 3회)을 인증 실패에 그대로 적용하면 안 되는 이유다.
- 1번: WinRM 인증 방식은 도메인 가입 여부와 이중 홉 필요 여부에 따라 달라지며, 잘못 선택하면 접속 자체가 실패한다.
  단일 입력 폼으로는 Hyper-V 연결을 성립시킬 수 없다.
- 4번: 같은 하이퍼바이저를 중복 등록하면 연결 ID가 달라 CI 식별 1순위 키가 갈리므로 자원이 이중 수집된다 (D-006).
- 5번: 연결 삭제로 수천 건의 자원 레코드와 변경 이력이 한 번에 사라지면 감사 추적이 끊긴다.

### 미결 사항

- **자격증명 암호화 키 관리 방식** (`spec.md` NFR-208) — 환경변수 / OS 키스토어 / 외부 KMS·Vault 중 선택. 키 교체 시 재암호화 절차 포함
- 연결 삭제 시 자원 처리 정책 최종 확정 (`spec.md` FR-109) — 권장안은 보존이나 사용자 확정 필요

## D-009. 웹 UI 제공과 Claude 기반 디자인 프로세스

| 항목 | 내용 |
|------|------|
| **결정일** | 2026-08-06 |
| **상태** | 확정 (검토자·라운드 횟수는 미결) |

### 결정

**1. 서비스 제공 방식** — 이 시스템은 웹 브라우저로 접속하는 포탈 화면을 통해 서비스를 제공한다 (`spec.md` FR-1201).
API만 제공하는 백엔드가 아니며, 운영자가 별도 도구 없이 브라우저에서 모든 조회·관리를 수행한다.
단, **자원을 변경하는 UI 요소는 제공하지 않는다** (FR-1206, D-005 연계).

**2. 디자인 도구 — Claude Design** — 코드 작성 전에 화면을 디자인해 합의한다 (FR-1212).
**이 원칙은 최소 기능 단계(Step 1)에도 그대로 적용된다** — Step 1의 자원 목록·연결 관리 2개 화면을
백엔드 구현과 병렬로 디자인하고 확정한 뒤 구현한다 (`plans/ROADMAP.md` §10).

```
Phase 0  ① 컨텍스트 주입   프로젝트 제약을 프롬프트로 명시
         ② 화면 디자인     Claude Design 캔버스 (Claude Desktop 사이드바 / claude.ai/design)
         ③ 검토           내부 URL 공유 → 운영팀 피드백 → 인라인 코멘트·직접 편집
         ④ 핸드오프       Export → Handoff to Claude Code → 로컬 코딩 에이전트
         ⑤ 토큰 고정      번들의 실제 토큰을 docs/03_design_system.md에 기록
Wave 4   ⑥ 구현           핸드오프 번들 기반으로 static/ 구현
```

**3. Phase 0을 앞에 배치** — 디자인은 백엔드 구현과 병렬 진행하되, Wave 4 착수 전에 확정한다.

### 근거

- **구현 후 화면 수정은 API 변경까지 유발한다.** 목록에 어떤 필드를 노출할지가 정해져야 응답 스키마가 확정된다
- **정적 목업으로는 검증할 수 없는 문제가 있다.** 이 프로젝트의 핵심 UI 규칙인
  "수집 불가"와 "값 없음"의 구분(FR-1204)은 **30행 목록 안에서 실제로 눈에 띄는지**를 봐야 판단할 수 있다.
  한 행만 그린 목업에서는 항상 잘 구분되어 보인다
- **Claude Design → Claude Code 핸드오프가 결정적이다.** 넘어오는 것이 스크린샷이나
  플러그인이 필요한 디자인 URL이 아니라 **컴포넌트 구조 spec + 캔버스에서 실제 사용된 디자인 토큰 +
  레이아웃 계층 + 참조 에셋**이므로, 코딩 에이전트가 "기존 작업을 이어받아" 구현한다.
  디자인을 보고 재구성하는 손실이 없다
- 토큰을 사람이 문서로 옮겨 적는 중간 단계가 사라져 **전달 오류가 줄어든다**
- 내부 URL 공유(보기·코멘트·편집 권한 구분)로 별도 배포 없이 이해관계자 검토가 이루어진다

### 사용 도구

## D-010. vCenter 연동 API 방식: SOAP 단일 경로

| 항목 | 내용 |
|------|------|
| **결정일** | 2026-08-06 |
| **상태** | 확정 |
| **관련** | D-001(스택), D-007(수집 방식), `spec.md` FR-606·CST-10 |

### 배경

vCenter에는 성격이 다른 접근 경로가 여러 개 있으며, 어느 것을 쓰느냐에 따라 **수집 가능한 속성과 성능 특성이 달라진다.**
D-001은 pyVmomi 채택만 기록했을 뿐 다른 경로를 배제한 근거가 없어, 요건이 추가될 때마다 재논의될 소지가 있었다.

| 방식 | 성격 | 커버리지 |
|---|---|---|
| **vSphere Web Services API (SOAP/vim25)** — pyVmomi | 전통적 관리 API. PropertyCollector 보유 | 인벤토리 전체, Custom Attributes, 스냅샷, 성능 |
| vSphere Automation API (REST) — vsphere-automation-sdk | 신규 기능 중심. **서버측 일괄 조회 메커니즘 없음** | vSphere Tags·카테고리, 콘텐츠 라이브러리, 어플라이언스 |
| VI/JSON (vSphere 8.0 U1+) | vim25를 OpenAPI 3.0 REST로 노출 | SOAP와 동일. **8.0 U1 미만 미지원** |

두 API는 대체 관계가 아니라 상호 보완 관계다. 전체 기능을 쓰려면 둘 다 필요하다는 것이 VMware의 공식 설명이다.

### 결정

**1. 수집 본체는 SOAP(vim25) 단일 경로로 한다.** vSphere Automation API(REST)는 도입하지 않는다.

**2. FR-606은 수집 대상을 분리하여 축소한다.**

| 항목 | 수집 경로 | 결정 |
|---|---|---|
| Notes | `config.annotation` (SOAP) | **수집** — 이미 계획 04 §5 반영 |
| Custom Attributes | `customValue` + `CustomFieldsManager.field` (SOAP) | **수집** — 계획 04 §5·§6에 추가 |
| **vSphere Tags** | vSphere Automation API (REST) **전용** | **Phase 2 보류** |

`ReaderCapabilities.supports_native_tags = False`는 "미지원 확정"이며, UI는 `해당 없음`으로 표시한다 (계획 03 §3.1).
도메인 모델의 `native_tags` 필드는 채울 경로가 없으므로 제거하고, `custom_attributes`로 교체한다 (계획 02 §5).

**3. 지원 vCenter 최소 버전은 6.5로 한다** (`spec.md` CST-10).

### 근거

- **PropertyCollector는 SOAP 전용이다.** REST에는 대응하는 서버측 일괄 조회가 없어 자원 수만큼 왕복이 발생하며,
  이는 D-007이 명시적으로 금지한 "개별 순회"에 해당한다. 수집 본체를 REST로 옮기는 것은 D-007 위반이다.
- **REST 추가 도입 비용이 요건 가치를 넘는다.** FR-606은 우선순위 `Could`이고 `spec.md` §2.2에서 공통 필수(✔) 표시가 없다.
  반면 도입 시 파급은 세션 관리 이원화, 연결 테스트 단계 추가, 의존성 추가, **그리고 `scripts/arch_check.py`의 읽기 전용 강제 규칙 재설계**에 이른다 (아래 참조).
- **VI/JSON은 버전 하한과 충돌한다.** 6.5를 지원하는 이상 8.0 U1 전용 프로토콜은 선택지가 아니다.
- Custom Attributes는 SOAP로 얻을 수 있으므로 추가 비용 없이 FR-606의 상당 부분을 충족한다.

### 트레이드오프

vSphere Tags를 운영에서 이미 활용 중인 조직이라면 메타데이터 초기값 자동 채움을 얻지 못한다.
대신 FR-601(포탈 메타데이터 입력)·FR-605(Excel 일괄 가져오기)로 대체 가능하다.

### 읽기 전용 강제와의 관계 (중요)

`scripts/arch_check.py`의 읽기 전용 검사는 **Python 메서드명 기반**이다 (D-005).
REST 클라이언트를 도입하면 `_post()`·`_delete()` 같은 HTTP 동사가 등장하는데,
REST 세션 생성 자체가 `POST /rest/com/vmware/cis/session`이므로 단순 금지도 불가능하다.
**SOAP 단일 경로 유지는 이 사각지대를 만들지 않는다는 부수적 이점이 있다.**

### 재검토 조건

아래 중 하나라도 성립하면 이 결정을 다시 연다.

- vSphere Tags 수집이 `Must`로 승격되는 경우
- 콘텐츠 라이브러리·VM 템플릿 인벤토리가 요건에 추가되는 경우
- 지원 vCenter 하한이 8.0 U1 이상으로 올라가는 경우 (VI/JSON 단일 경로 전환 검토 가치 발생)

REST를 추가할 경우 **pyVmomi 세션 ID를 Automation SDK에서 재사용하는 통합 인증**을 우선 검토한다.
자격증명 노출면을 늘리지 않고 붙일 수 있다. 단, 6.5/6.7은 `/rest/`, 7.0+는 `/api/`로 엔드포인트가 다르므로
버전 분기가 필요하다.

### 미결 사항

- **pyVmomi 최신 버전의 vSphere 6.5 호환 범위** — 6.5는 VMware EOL 버전이라 최신 pyVmomi가 호환을 보증하지 않을 수 있다.
  대상 환경의 실제 버전 분포를 확인한 뒤 pyVmomi 버전을 고정한다 (`plans/01` 의존성, `docs/00_research_notes.md` §11-9)
- 6.5에서 존재하지 않는 속성 경로 (`config.createDate` 등) — 계획 04 §5 실측 시 함께 확인

## D-011. 단계적 구현에서 축소하지 않는 것: 식별 구조·게스트 폴백·응답 계약

| 항목 | 내용 |
|------|------|
| **결정일** | 2026-08-07 |
| **상태** | 확정 |
| **관련** | D-006(CI 식별), D-007(수집 경로), `plans/ROADMAP.md` §4.1·§7.3·§7.4·§9.2 |

### 배경

`plans/ROADMAP.md`는 영역별 계획서를 동작하는 단계로 잘랐고, Step 1(MVP)에서 무엇을 빼는지를 §4에 정의했다.
기준은 "기능의 크기"가 아니라 **나중에 추가할 때의 파괴력**이다.

이 기준으로 Step 1 설계를 최종 설계(계획 02·06·07·08·12)와 대조한 결과, **파괴력이 큰데도 빠진 항목 4건**이 발견되었다.
ROADMAP §4.1이 근거로 계획 06 §2.7(`resource_identities`)을 지목하면서 정작 §7 DDL에는 넣지 않은 것처럼,
누락은 판단의 결과가 아니라 대조 누락이었다.

### 결정

Step 1은 컬럼과 기능을 축소하되, **아래 4가지는 최종 형태로 만든다.**

**1. `resource_identities` 테이블과 식별키 조회 구조** (계획 06 §2.7·§3)

`INSERT ... ON CONFLICT (connection_id, native_id) DO UPDATE`로 구현하지 않는다.
계획 06 §3.1의 흐름(`build_vm_identity_keys` → `_find_by_identity` → `_sync_identities`)을 그대로 구현하고,
**키 생성만 1순위로 제한**한다. 2순위(BIOS UUID)는 Step 5, 3순위(MAC+이름)는 Step 4에서
`build_vm_identity_keys`에 행을 더하는 것으로 끝난다.

`uq_vm_native` 제약은 그대로 유지한다. 식별키 조회가 논리적 방어, DB 제약이 최후 방어다.

**2. `guest_observed_at` 컬럼과 게스트 값 폴백** (계획 02 §5.1, 06 §3.3)

`GuestInfo.with_fallback`을 Step 1 upsert 경로에 적용하고, 관측 시각을 저장할 컬럼을 함께 만든다.

**3. API 응답 계약을 최종 형태로 고정** (계획 07 §2, 08 §3.1·§6.3)

- 페이징: `page`/`size`가 아니라 `offset`/`limit`/`sort_by`/`sort_desc` + `PagedResponse{items,total,offset,limit}`
- 정렬 컬럼은 `Page.ALLOWED_SORT` 화이트리스트로 검증
- 게스트 정보는 평면 필드가 아니라 중첩 `GuestInfoResponse`, `unavailable_reason` 문자열은 **서버가 생성**

**4. `pg_trgm` 확장을 Alembic 초기 리비전에 포함**

실제 사용은 Step 4(통합 검색)지만 생성 시점을 Step 1로 앞당긴다.

**명시적으로 Step 1에서 빼는 것** — 위 구조 안에서 나중에 추가되는 것들:

| 항목 | 도입 Step | 이유 |
|---|---|---|
| `DuplicateCandidate` 분기 | 3 | 연결이 하나뿐이면 다른 연결과의 매칭이 발생하지 않는다 |
| 식별 2·3순위 키 | 5 · 4 | 함수 반환 행 추가로 끝난다 |
| `resource_changes` | 8 (필요 시 3) | 이력은 소급되지 않는다 — 아래 한계 참조 |

### 근거

네 항목은 "나중에 넣기 어려운 이유"가 서로 다르며, 각각이 독립적으로 성립한다.

| 항목 | 나중에 넣으면 |
|---|---|
| 식별 구조 | "제약 위반을 잡아 갱신"에서 "식별키로 찾아 분기"로 **알고리즘이 바뀐다.** upsert 전면 재작성 |
| 게스트 폴백 | 도구가 꺼진 VM을 재수집하는 순간 이전 값이 NULL로 덮어써진다. **덮어쓴 값은 복구 불가** |
| 응답 계약 | API와 UI를 동시에 고쳐야 한다. Step 4 시점에는 화면이 5개다 |
| `pg_trgm` | 확장 생성은 상위 DB 권한을 요구한다. **권한 승인은 구현보다 오래 걸린다** |

두 번째가 가장 무겁다. 나머지 셋은 비싼 재작업이지만, 이것만 **되돌릴 수 없다.**
이는 D-006이 정한 "수집 불가는 값 없음이 아니다"를 데이터 수준에서 지키는 문제이기도 하다.
도구가 멈춘 것이지 VM의 OS가 사라진 것이 아니다.

네 번째는 코드 문제가 아니라 **조직 절차 문제**라서 앞당긴다.
Step 4에서 처음 부딪히면 그때부터 권한 신청이 시작된다.

### 한계 (인지하고 진행할 것)

**변경 이력은 소급되지 않는다.** 계획 12의 diff는 upsert 시점에 생성되므로,
`resource_changes`를 Step 8에서 도입하면 **Step 1~7 동안의 vCPU 변경·vMotion·이름 변경은 영구히 기록되지 않는다.**
테이블은 나중에 만들 수 있지만 지나간 변경은 되살릴 수 없다.

이력의 시작점을 앞당겨야 한다면 Step 3(수집 스케줄러 도입)에서 `resource_changes`를 함께 만든다.
Step 1에 넣지 않은 것은 수동 수집만 있는 동안에는 변경 발생 빈도가 낮고,
`_merge_guest`와 달리 **나중에 만들어도 그때부터의 이력은 온전하기** 때문이다.

### 고려한 대안

| 대안 | 채택하지 않은 이유 |
|------|-------------------|
| Step 1은 최단 경로로 만들고 Step 3에서 리팩터링 | 리팩터링 대상이 upsert(데이터 정합성의 핵심)와 API 계약(UI 연동면)이다. 실환경 데이터가 들어간 뒤 바꾸는 비용이 지금보다 훨씬 크다 |
| 최종 스키마를 통째로 만들고 컬럼만 비워둠 | 쓰지 않는 테이블 12개의 ORM·마이그레이션을 유지해야 한다. **파괴력이 없는 것까지 앞당길 이유가 없다** |
| 게스트 폴백을 Step 3(스케줄러)으로 | 자동 수집이 시작되면 폴백 없는 덮어쓰기가 주기마다 반복된다. 수동 수집만 하는 Step 1~2가 오히려 유일한 안전 구간이다 |

## D-012. Hyper-V 연동: 관리 콘솔 계열별 2개 수집 경로

| 항목 | 내용 |
|------|------|
| **결정일** | 2026-08-07 |
| **상태** | 확정 (2026-08-07 SCVMM 도입 확정 + 읽기 전용 계정 방침 확정으로 갱신) |
| **관련** | D-003(Protocol), D-005(읽기 전용), D-006(CI 식별), `spec.md` FR-103·NFR-201·CST-03·06·09, `plans/05` |

### 배경

Microsoft 환경의 가상화 관리 콘솔은 두 계열이다.

| 계열 | 도구 | 인벤토리 가시성 |
|---|---|---|
| **Hyper-V 관리자** | Hyper-V Manager, 장애 조치 클러스터 관리자, Windows Admin Center | 호스트 또는 클러스터 단위 |
| **SCVMM** | System Center Virtual Machine Manager | **fabric 전체** (관리 대상 호스트·클러스터 전부) |

기존 계획은 `ConnectionKind`에 `scvmm`을 정의해 두고도 **"CST-09 확정 전까지 미구현"**으로 두어,
리더 팩토리가 `NotImplementedError`를 던지는 상태였다. SCVMM 환경에서는 포탈이 아예 동작하지 않는다.

### 결정

**0. SCVMM을 도입한다** (2026-08-07 확정, CST-09 해소).
**경로 B가 Hyper-V 수집의 주 경로**이며, 경로 A는 SCVMM이 관리하지 않는 독립 호스트에만 사용한다.
SCVMM 구축 완료가 Hyper-V 수집 착수의 선행 조건이다 (`plans/ROADMAP.md` §20.1).

**1. 두 수집 경로를 모두 구현한다.** 다만 착수 순서는 경로 B가 먼저다.

| 경로 | `ConnectionKind` | 접속 대상 | PowerShell 모듈 | 조회 위상 | 적용 대상 |
|---|---|---|---|---|---|
| **B (주)** | `scvmm` | SCVMM 관리 서버 | `VirtualMachineManager` | 1회 호출로 전체 | SCVMM 관리 fabric |
| A (보조) | `hyperv-host` · `hyperv-cluster` | Hyper-V 호스트 / 클러스터 노드 | `Hyper-V`, `FailoverClusters` | 호스트별 순회 | SCVMM 미관리 독립 호스트 |

**2. 같은 패키지(`src/infrastructure/hyperv/`)에 둔다.** 별도 최상위 어댑터로 분리하면
WinRM 세션·실행기를 공유하기 위해 어댑터 간 import가 생기고, 이는 arch-check 특화 규칙 2 위반이다.
두 경로는 **같은 WinRM 스택을 쓰는 한 어댑터의 두 수집 전략**이다.

**3. `native_id`는 양쪽 모두 Hyper-V VM GUID로 통일한다.**
SCVMM의 `Get-SCVirtualMachine`은 `ID`(VMM 객체 ID)와 `VMId`(VM GUID)를 함께 반환하는데, **`VMId`를 쓴다.**

**4. SCVMM이 있으면 SCVMM만 등록한다.** 두 경로로 같은 VM을 수집하면 `connection_id`가 달라
CI 식별 1순위 키가 갈리고 자원이 이중 생성된다 (D-006). UI 등록 화면에 경고를 표시한다.

**5. 경로 B를 먼저 구현한다.** SCVMM 연결 1개가 호스트 연결 수십 개를 대신한다.
경로 A는 SCVMM 미관리 호스트가 **실제로 확인된 뒤** 착수한다 (`plans/ROADMAP.md` §20.1).

**6. VMM DB를 갱신하는 cmdlet을 호출하지 않는다.** 특히 `Read-SCVirtualMachine`은
이름이 `Read-`로 시작하지만 **새로 고침(쓰기) 동작**이다. VMM 새로 고침 주기는 VMM 관리자의 영역이다.

**7. 읽기 전용 계정은 두 계층으로 구성한다** (NFR-201, D-005의 1번 방어).

접속 계정이 대상 서버의 관리자여서는 안 된다. **WinRM 접속 권한**과 **대상 시스템 조회 권한**을 따로 본다.

| | 계층 1 — WinRM 접속 | 계층 2 — 조회 권한 |
|---|---|---|
| **경로 B (SCVMM)** | SCVMM 서버의 `Remote Management Users` 그룹 (**로컬 관리자 아님**) | VMM User Role **`Read-Only Administrator`** |
| **경로 A (호스트)** | **JEA 제약 엔드포인트** — 가상 계정으로 실행 | JEA `VisibleCmdlets`에 조회 cmdlet만 나열 |

**경로 A는 JEA(Just Enough Administration)를 쓴다.** 대상 호스트에 제약 세션 구성을 등록하고,
포탈 계정은 비관리자로 두며 세션은 **가상 계정**으로 실행한다.

노출 방식은 **역할 기능 파일에 수집 함수를 정의하고 `VisibleFunctions`로 그 함수만 노출**한다.
개별 cmdlet을 `VisibleCmdlets`로 여는 방식이 아니다.

```powershell
# 역할 기능 파일(.psrc) — 호스트에 배포
FunctionDefinitions = @(
    @{ Name = 'Get-WzoneVmInventory';   ScriptBlock = { <계획 05 §6.1 스크립트> } }
    @{ Name = 'Get-WzoneHostInfo';      ScriptBlock = { <§6.2> } }
    @{ Name = 'Get-WzoneClusterNodes';  ScriptBlock = { <§6.3> } }
    @{ Name = 'Get-WzoneStorage';       ScriptBlock = { <§6.4> } }
)
VisibleFunctions = 'Get-Wzone*'
```

**함수 방식을 택한 이유는 JEA의 언어 모드 제약 때문이다.** 제약 세션은 `NoLanguage` 또는
`ConstrainedLanguage`로 동작하는데, 계획 05의 수집 스크립트는 `[PSCustomObject]` 구성과
KVP의 `[xml]` 캐스팅을 쓴다. `[xml]`은 ConstrainedLanguage 허용 타입이 아니므로
**스크립트를 그대로 보내는 방식은 JEA에서 실행되지 않는다.**
역할 기능 파일 안의 함수는 정의 시점에 신뢰되므로 이 제약을 받지 않는다.

부수 효과로 **노출면이 cmdlet 십여 개에서 함수 4개로 줄어든다.** 감사 관점에서도 낫다.
대신 **수집 스크립트가 호스트에 배포되므로, 스크립트를 바꾸면 호스트의 JEA 구성도 갱신해야 한다.**

**경로 B의 계층 1을 빠뜨리지 않는다.** VMM 역할이 Read-Only여도 접속 계정이 SCVMM 서버의
로컬 관리자면 **그 서버에서 무엇이든 할 수 있다.** VMM 역할은 VMM 안에서만 유효하다.
SCVMM 서버에도 JEA를 적용하는 것이 더 낫지만(`Get-SC*`만 노출), `Remote Management Users` +
Read-Only Administrator 조합으로도 요건은 충족된다.

**8. 경로 A를 쓰기 전에 SCVMM 편입을 먼저 검토한다.**

JEA 구성은 호스트마다 배포·유지해야 하고, 수집 스크립트가 바뀌면 갱신 대상이 된다.
**대부분의 경우 그 호스트를 SCVMM에 등록하는 편이 비용이 낮다.**

```
독립 Hyper-V 호스트 발견
   └─ SCVMM에 편입 가능한가?
        ├─ 예   → 편입한다. 경로 A를 쓰지 않는다        ← 우선
        └─ 아니오 (격리망·DMZ·검증 전용 등)
              └─ 경로 A + JEA로 등록
```

**JEA 구축 전에는 해당 호스트를 등록하지 않는다.** 관리 권한 계정으로 임시 운영하지 않는다.
수집 공백이 생기더라도, 전원·삭제 권한을 가진 자격증명을 포탈이 보관하는 것보다 낫다.

### 근거

- **SCVMM은 Microsoft의 기본 해법이다** (`docs/00_research_notes.md` §7.2). 다수 호스트 환경에서
  호스트별 원격 PowerShell 순회는 수집 시간이 호스트 수에 비례해 늘어난다. SCVMM은 이를 1회 호출로 대체한다
- **읽기 전용 계정 요건(NFR-201)이 경로에 따라 성패가 갈린다.** SCVMM에는
  `Read-Only Administrator` 역할이 있어 D-005의 1번 방어(권한 차단)가 성립한다.
  경로 A의 `Hyper-V Administrators`는 전원·삭제 권한을 함께 가지므로 성립하지 않는다
- **`VMId`를 쓰는 이유는 두 가지다.** VMM 객체 ID는 SCVMM 재설치·재등록으로 바뀔 수 있고,
  두 경로가 같은 VM에 같은 식별자를 주어야 SCVMM 도입·제거 시 중복 후보 감지가 동작한다
- SCVMM을 도입해도 **모든 Hyper-V 호스트가 SCVMM에 등록된다는 보장은 없다.**
  DMZ·격리망·검증용 단독 호스트가 남는 것이 일반적이므로 경로 A를 버리지 않는다 (CST-03)

**JEA를 선택한 근거 (경로 A)**

- **Microsoft가 이 문제를 위해 만든 표준 기능이다.** "관리 권한 없이 특정 cmdlet만 허용"이 JEA의 목적이며,
  세션이 **가상 계정**으로 실행되므로 포탈이 보관하는 자격증명 자체가 관리자 권한을 갖지 않는다.
  D-005의 1번 방어(권한 차단)가 실제로 성립하는 유일한 선택지다
- **포탈이 실행할 스크립트가 이미 확정되어 있다** (`plans/05` §6). 그대로 역할 기능 파일의
  함수 본문으로 옮기면 되므로 설계 비용이 크지 않다
- **SCVMM 도입으로 적용 대상이 소수가 되었다.** 호스트 수십 대에 JEA를 배포·유지해야 했다면
  현실성이 없었을 것이다. 독립 호스트 몇 대라면 감당 가능하다.
  **SCVMM 결정이 JEA 선택을 가능하게 했다** — 순서가 반대였다면 결론이 달랐다
- 대안이었던 "WMI 권한만 부여"는 `Get-VHD` 등가물이 `Msvm_ImageManagementService`의 **메서드 호출**을
  요구한다. 메서드 실행 권한은 WMI에서 조회 권한과 별개이며, 이름도 조회처럼 보이지 않아
  **읽기 전용임을 검증하기 어렵다.** 감사 관점에서 JEA의 명시적 허용 목록이 낫다

### 트레이드오프

**게스트 정보의 신선도가 경로에 따라 다르다.** 경로 A는 KVP를 직접 읽지만, 경로 B는 VMM DB의 캐시값을 받는다.
VMM 새로 고침이 멈춰 있으면 포탈은 최신 수집인데 값은 오래된 상태가 된다.
포탈 수집 시각과 VMM `ModifiedTime`이 크게 벌어지면 경고한다 (`plans/05` §8.5).

또한 SCVMM의 `OperatingSystem`은 출처가 불확실하여 **구성값(`OsSource.VM_CONFIG`)으로 보수적으로 매핑**한다.
UI에 `(구성값)`이 병기되므로(FR-304) 사용자가 실측값이 아님을 알 수 있다.

### 고려한 대안

| 대안 | 채택하지 않은 이유 |
|------|-------------------|
| SCVMM만 지원 | SCVMM에 등록되지 않은 독립 호스트가 남는다 (CST-03) |
| 호스트 직접 수집만 지원 (현행 유지) | SCVMM 환경에서 호스트를 일일이 등록해야 하고, 읽기 전용 계정을 만들 수 없다 |
| SCVMM을 별도 최상위 어댑터로 분리 | 세션·실행기 공유를 위한 import가 arch-check 규칙 2 위반이 된다 |
| `native_id`에 VMM 객체 ID 사용 | SCVMM 재설치 시 전 자원이 중복 생성된다 |

**읽기 전용 계정 대안** (결정 7번)

| 대안 | 채택하지 않은 이유 |
|------|-------------------|
| WMI 네임스페이스 권한만 부여 + CIM 쿼리로 재작성 | `Get-VHD` 등가물이 WMI **메서드 호출**을 요구한다. 메서드 실행 권한은 조회 권한과 별개이고, 읽기 전용임을 감사로 확인하기 어렵다. 스크립트 재작성 비용도 크다 |
| `Hyper-V Administrators` 권한 수용 + 감사로 통제 | **NFR-201 미충족.** 전원·삭제 권한을 가진 자격증명을 포탈이 보관하게 되며, D-005의 3겹 방어 중 1번이 무너진다 |
| SCVMM 서버에 로컬 관리자로 접속 (VMM 역할만 제한) | VMM 역할은 VMM 안에서만 유효하다. 서버 자체에 대한 관리 권한이 남는다 |

### 미결 사항

- `plans/05` §4.2·§7.2의 `[검증 필요]` 항목 (`VMId` 존재 여부, `IPv4Addresses` 출처, `OperatingSystem` 갱신 시점)
- **pypsrp의 JEA 세션 구성 지원** — `RunspacePool`에 `configuration_name`을 지정해 JEA 엔드포인트에
  접속할 수 있는지 확인한다. 불가하면 경로 A의 접속 계층을 재검토해야 한다 (`docs/00_research_notes.md` §11-17)
- **JEA 함수 반환값의 직렬화** — 제약 세션은 반환 객체를 역직렬화된 형태로 준다.
  함수 안에서 `ConvertTo-Json`까지 마치고 **문자열을 반환**하면 이 문제를 피할 수 있으나,
  실제 동작을 확인한 뒤 함수 시그니처를 확정한다 (`docs/00_research_notes.md` §11-18)
- **SCVMM 구축 일정** — Hyper-V 수집(Step 5)의 선행 조건이다. 구축이 지연되면 Step 5를 뒤로 미루고
  다른 Step을 먼저 진행한다. **독립 호스트를 관리 권한으로 임시 수집하는 우회는 하지 않는다**

## D-013. 시스템 관리 DB: PostgreSQL 단일 저장소

| 항목 | 내용 |
|------|------|
| **결정일** | 2026-08-07 |
| **상태** | 확정 (2026-08-07 버전 확정으로 갱신. 배포 형태·백업 정책은 미결) |
| **관련** | D-002(계층), D-007(조회·수집 분리), D-011(Step 1 스키마), `spec.md` CST-08, `plans/06` |

### 배경

`spec.md` 기술 스택과 `CLAUDE.md`에 "PostgreSQL + SQLAlchemy(async)"가 적혀 있고 `plans/06`이
그 전제로 DDL을 작성했으나, **선정 근거와 제약이 결정으로 기록되어 있지 않았다.**
`plans/06`의 DDL은 이미 PostgreSQL 고유 기능에 깊이 의존하므로, 사실상 확정된 것을 명문화한다.

### 결정

**1. 인벤토리·메타데이터·변경 이력·감사 로그를 모두 PostgreSQL 하나에 저장한다.**
자원 유형별로 저장소를 나누지 않는다.

**2. 접근 스택은 SQLAlchemy 2.x(async) + asyncpg + Alembic으로 고정한다.**

**3. PostgreSQL 고유 기능 사용을 허용한다.** 이식성보다 조회 성능과 데이터 정합성을 우선한다.

| 기능 | 용도 | 대체 시 비용 |
|---|---|---|
| `JSONB` | Custom Attributes (`plans/06` §2.3) | 별도 키·값 테이블 + 조인 |
| `INET` | IP 주소 (`vm_adapter_ips`) | 문자열 저장 시 정규화·검색 품질 저하 |
| `TEXT[]` + GIN | 메타데이터 태그 | 태그 테이블 추가 |
| `pg_trgm` + GIN | 이름·호스트명 유사 검색 (FR-403) | `LIKE` 전체 스캔 |
| 부분 인덱스 (`WHERE lifecycle='active'`) | 조회의 대부분이 활성 자원 | 인덱스 크기·적중률 손해 |
| `TIMESTAMPTZ` | UTC 저장 (공통 규칙 3.4) | 시각 보정 로직 필요 |

**4. Redis는 캐시·작업 큐 전용이며 원본 데이터를 두지 않는다.** Redis가 없어도 조회는 동작해야 한다.
도입 시점은 데이터 규모 확인 후이며, Step 1에는 없다 (`plans/ROADMAP.md` §4.2).

**5. 확장 생성 권한을 Step 1에 확인한다.** `CREATE EXTENSION pg_trgm`은 상위 권한을 요구하므로
Alembic 초기 리비전에 포함해 권한 문제를 앞당겨 드러낸다 (D-011).

**6. 버전은 PostgreSQL 17을 표준으로 하고, 16을 하한으로 한다** (2026-08-07 확정).

| 버전 | 커뮤니티 지원 종료 | 판정 |
|---|---|---|
| 14 이하 | 14는 2026-11 | **불가** — 실제 운영 개시(Step 7 이후) 시점에 이미 지원이 끝난다 |
| 15 | 2027-11 | 권장하지 않음 — 운영 시작 직후 메이저 업그레이드가 필요해진다 |
| **16** | 2028-11 | **하한.** 사내에 기존 인스턴스가 있으면 수용 |
| **17** | 2029-11 | **표준.** 신규 구축은 이것으로 한다 |
| 18 이상 | — | 금지하지 않되, 조직의 백업·모니터링 도구 지원을 확인한 뒤 채택 |

§3의 기능(JSONB·INET·배열·GIN·pg_trgm·부분 인덱스)은 모두 오래전부터 제공되므로
**버전 선택 기준은 기능이 아니라 지원 기간과 이 워크로드에 유효한 성능 개선**이다.

17을 표준으로 하는 실질적 이유 세 가지:

| 개선 | 이 프로젝트에서의 의미 |
|---|---|
| B-tree 다중값 `IN` 검색 최적화 | 목록 조회 필터가 **전부 다중값**이다 — `connection_id`, `power_state`, `lifecycle`, `environment` 등 (계획 08 §6.1). 가장 잦은 쿼리 형태가 직접 이득을 본다 |
| VACUUM 메모리 관리 개선 | 매 수집마다 전 행의 `last_seen_at`을 UPDATE하므로 **dead tuple이 대량 발생**하는 워크로드다 (계획 06 §3) |
| 증분 백업 (`pg_basebackup`) | 백업 정책 수립(아래 미결)에서 선택지가 넓어진다 |

### 근거

- **읽기 전용 인벤토리 포탈의 부하는 복잡한 필터·검색 조회에 몰린다.** 부분 인덱스와 GIN을 쓸 수 있는지가
  NFR-101(1초 이내)의 달성 가능성을 좌우한다
- 수집 경로와 조회 경로가 분리되어 있어(D-007) **쓰기는 배치 upsert, 읽기는 인덱스 조회**로 성격이 뚜렷하다.
  관계형 DB에 잘 맞는 형태이며 NoSQL을 도입할 이유가 없다
- 변경 이력·감사 로그는 **트랜잭션 일관성**이 요구된다. 수집과 이력이 같은 트랜잭션에서 커밋되어야
  "자원은 갱신됐는데 이력이 없는" 상태가 생기지 않는다
- 조직의 collectorinfra 프로젝트와 동일 스택이라 운영 노하우를 재사용할 수 있다 (D-001과 같은 근거)

### 미결 사항

**이 항목들은 계획서 어디에도 없다. 배포 전에 확정해야 한다.**

- **배포 형태** — 전용 서버 / 컨테이너 / 사내 공용 DB 인스턴스 (`spec.md` CST-08 `[TODO]`와 연동).
  공용 인스턴스면 확장 생성 권한과 DDL 권한 확보가 별도 절차다 (`plans/ROADMAP.md` §15.4)
- **백업·보존 정책** — **인벤토리 정보 자체가 민감 정보이고(NFR-206), 백업에는 자격증명 암호문이 포함된다.**
  백업 보관 위치·암호화·보존 기간을 자격증명 키 관리 방식(D-008 미결)과 함께 정해야 한다
- **용량 산정** — NFR-104(관리 규모)가 `[TODO]`라 산정 불가. Step 2 실측 후 확정
- **가용성 요구** — 이중화 필요 여부. 조회 전용 포탈이라 단일 인스턴스 + 백업으로 충분할 가능성이 높으나
  운영 정책 확인 필요
- **Redis 버전·라이선스** — 7.4 이후 라이선스 변경으로 사내 정책에 걸릴 수 있다. Valkey 대체 가능 여부 포함.
  Step 3 이전에 확인

### 고려한 대안

| 대안 | 채택하지 않은 이유 |
|------|-------------------|
| MySQL / MariaDB | 부분 인덱스 부재, 배열·`INET` 타입 부재. `plans/06`의 인덱스 설계를 다시 짜야 한다 |
| MongoDB 등 문서 DB | 자원 간 관계 탐색(호스트 → VM, 클러스터 → 호스트)과 변경 이력의 트랜잭션 일관성에 불리 |
| SQLite | 단일 파일이라 초기 개발은 편하나, 동시 수집·조회와 부분 인덱스·GIN이 필요한 요건에 맞지 않는다 |
| 시계열 DB 병행 (변경 이력용) | 저장소가 둘이 되어 운영·백업·조회 조인이 복잡해진다. 변경 이력의 규모가 그 비용을 정당화하지 못한다 |

## D-014. 계정 관리: 가입 신청 + 관리자 승인, 인증은 Step 1 기본 기능

| 항목 | 내용 |
|------|------|
| **결정일** | 2026-08-07 |
| **상태** | 확정 |
| **관련** | D-005(읽기 전용), D-009(웹 UI), `spec.md` FR-1001~1008·FR-1213, `plans/09`, `plans/ROADMAP.md` |

### 배경

`plans/ROADMAP.md`는 인증·RBAC를 Step 7로 두고, 그 전까지는 "구현자와 검토자만 접근하는 검증용"으로 운영한다고 정했다.
사용자가 **로그인·가입·관리자 화면을 기본 기능으로 요구**하여 이를 Step 1로 옮긴다.

### 결정

**1. 인증·인가·계정 관리를 Step 1(MVP) 범위에 포함한다.**
로그인, 가입 신청, 관리자 승인, 역할 부여, 조회 범위 부여, 감사 로그(계정·로그인 영역)가 Step 1에 들어간다.
`AccessScope`도 이때 함께 도입한다 — 저장소 조회 메서드의 첫 인자로 들어가므로 나중에 넣으면 전 시그니처를 고쳐야 한다.

**2. 셀프 가입은 "신청"이며 즉시 접근 권한이 되지 않는다.**

```
가입 신청 → pending(승인 대기)
              ├─ 관리자 승인 → active   (이때 역할·조회 범위를 함께 부여)
              └─ 관리자 거부 → rejected
active ──── 관리자 비활성화 → disabled ──── 재활성화 → active
```

- `pending`·`rejected`·`disabled` 계정은 **로그인할 수 없고 어떤 조회 API도 호출할 수 없다.**
- 승인 시 역할을 지정하지 않으면 `viewer` + **빈 조회 범위**가 되어 아무것도 보이지 않는다 (기본 거부).
- **계정은 삭제하지 않고 `disabled`로 둔다.** 감사 로그의 행위자 추적이 끊기지 않아야 한다 (FR-1004).

**3. JWT는 `httpOnly` 쿠키로 전달한다.** `SameSite=Strict`, 운영에서는 `Secure`.

**4. 계정 상태 검사는 비밀번호 검증 뒤에 한다.**

```
username 조회 → (없으면) 더미 해시 검증 → 통일 메시지
             → 잠금 확인 → 비밀번호 검증 → 실패 시 통일 메시지
             → 성공 후에야 status 판정 → 상태별 안내 메시지
```

### 근거

- **인벤토리 정보는 그 자체로 공격 표면 정보다** (NFR-206). IP·호스트명·OS 목록은 침투 경로 설계에 그대로 쓰인다.
  누구나 가입해 즉시 조회할 수 있으면 읽기 전용(D-005)으로 얻은 안전성이 무의미해진다.
- **2번의 기본 거부는 FR-1003과 같은 원칙이다.** `user_connection_scopes`에 행이 없으면 아무것도 보이지 않는다.
- **3번**: 인벤토리 정보의 민감도를 고려하면 XSS 한 번에 토큰이 전량 유출되는 `localStorage` 저장은 위험이 크다.
  브라우저 UI가 주 사용처이고 외부 연동은 별도 API 키(FR-1104)를 쓰므로 쿠키 방식의 단점이 작다.
- **4번**: 상태 검사를 비밀번호 검증보다 먼저 하면, 비밀번호를 모르는 공격자도 "승인 대기 중"이라는 응답으로
  **계정 존재를 확인**할 수 있다. 검증 뒤로 옮기면 계정 열거를 막으면서도 정당한 사용자에게는 정확한 사유를 알려줄 수 있다.
  (`plans/09` §4.3의 기존 순서를 이 결정에 맞게 수정했다.)

### 트레이드오프

Step 1의 범위가 커진다 — 화면 3개(로그인·가입·사용자 관리)와 테이블 3개(`users`, `user_connection_scopes`, `audit_events`)가 추가된다.
대신 Step 2(실환경 적용)부터 **실제 사용자에게 열어도 되는 상태**가 되고, `AccessScope`를 뒤늦게 주입하는 대규모 리팩터링을 피한다.

### 고려한 대안

| 대안 | 채택하지 않은 이유 |
|------|-------------------|
| 셀프 가입 즉시 활성화 | 인벤토리 조회 권한이 무통제로 열린다. NFR-206과 정면 충돌 |
| 가입 없이 관리자가 계정 생성만 | 사용자 요구(가입 기능)를 충족하지 못한다. 관리자 수작업 부담도 크다 |
| 이메일 인증 후 자동 활성화 | 사내 메일 도메인 확인은 "조직 구성원"만 증명할 뿐 **조회 권한을 정당화하지 못한다.** 메일 발송 인프라 의존도 생긴다 |
| `localStorage` + Bearer 헤더 | XSS 시 토큰 전량 유출. 구현은 쉬우나 이 시스템의 민감도에 맞지 않는다 |
| 계정 물리 삭제 허용 | 감사 로그의 행위자 참조가 끊긴다 (FR-1004) |

- **가입 시 수집할 정보** — 현재는 아이디·표시이름·이메일·비밀번호. 사번·부서를 받을지는 운영 정책에 따름
- **승인 알림** — 승인·거부를 신청자에게 알리는 수단(메일 등). Step 1은 화면에서 상태 확인만 제공
- 외부 인증(FR-1005) 도입 시 가입 화면의 존치 여부 — LDAP/SSO를 쓰면 가입 대신 최초 로그인 시 `pending` 생성이 자연스럽다

## D-015. 비밀번호 해시: passlib 대신 bcrypt 직접 사용

| 항목 | 내용 |
|------|------|
| **결정일** | 2026-08-07 |
| **상태** | 확정 |
| **관련** | D-014, `plans/09` §4.1, `src/infrastructure/security/password.py` |

### 배경

계획 09 §4.1은 `passlib`의 `CryptContext(schemes=["bcrypt"])`를 지정했다.
Step 1 구현 중 실제 환경(`passlib` 1.7.4 + `bcrypt` 5.0)에서 **해시 생성 자체가 실패**했다.

```
ValueError: password cannot be longer than 72 bytes, truncate manually if necessary
  passlib/handlers/bcrypt.py:380  detect_wrap_bug()
```

`passlib`이 백엔드 초기화 시 실행하는 자체 점검(`detect_wrap_bug`)이 72바이트를 넘는 입력을
`bcrypt`에 넘기는데, `bcrypt` 4.1+가 이를 잘라내지 않고 예외로 바꾸면서 초기화가 깨진다.
`passlib`은 2020년 이후 릴리스가 없어 수정을 기대할 수 없다.

### 결정

**`bcrypt`를 직접 사용한다.** 공개 함수 시그니처는 계획 09와 동일하게 유지한다.

| 함수 | 역할 |
|---|---|
| `hash_password(SecretStr) -> str` | 정책 검증 후 해시 |
| `verify_password(SecretStr, str) -> tuple[bool, str \| None]` | 검증 + 필요 시 재해시 |
| `fake_verify()` | 존재하지 않는 계정용 타이밍 완화 (계획 09 §4.3) |
| `validate_password_policy(SecretStr)` | 10자 이상 / 72바이트 이하 |
| `generate_temporary_password()` | 임시 비밀번호 (FR-1008) |

`needs_update` 대체로 저장된 해시의 cost 파라미터를 직접 읽어 비교한다(`_needs_rehash`).

### 근거

- **`passlib` 고정(pin)은 더 나쁜 선택이다.** `bcrypt<4.1`로 내리면 보안 패치를 못 받는 라이브러리
  두 개에 묶인다. 이 시스템은 다수 하이퍼바이저 자격증명을 모으므로 인증 스택을 정체된
  의존성에 두면 안 된다.
- **절단 문제를 숨기지 않는다.** 72바이트 초과를 조용히 자르면 서로 다른 비밀번호가 같은 해시를
  갖는다. `validate_password_policy`가 입력 단계에서 거부하므로 이 경로가 아예 없다.
- 대체 알고리즘(argon2 등) 전환은 이 결정과 독립적이다. 필요해지면 같은 함수 시그니처 뒤에서 바꾼다.

### 고려한 대안

| 대안 | 채택하지 않은 이유 |
|------|-------------------|
| `bcrypt<4.1` 고정 | 정체된 라이브러리 2개에 인증 스택을 묶는다 |
| `argon2-cffi`로 전환 | 계획 09 전반이 bcrypt 전제(72바이트 제한 안내 등). 지금 바꿀 이유가 없다 |
| 72바이트 초과를 잘라서 통과 | 서로 다른 비밀번호가 같은 해시가 된다 |

## D-017. 쓰기 트랜잭션은 요청 핸들러에서 커밋한다

| 항목 | 내용 |
|------|------|
| **결정일** | 2026-08-07 |
| **상태** | 확정 |
| **관련** | D-002, `src/api/deps.py`, `plans/08` |

### 배경

DB 세션을 FastAPI의 `yield` 의존성으로 제공하고 teardown에서 커밋하는 흔한 구성으로 시작했다.
실서버(uvicorn)에서 **등록 직후 목록 조회에 방금 만든 레코드가 빠지는** 현상이 재현되었다.

```
iter 0: create=201 list_count=2 (expected 2)
iter 1: create=201 list_count=2 (expected 3)   ← 한 건씩 밀린다
iter 2: create=201 list_count=3 (expected 4)
```

teardown 커밋이 **응답이 나간 뒤에** 실행되어, 클라이언트가 곧바로 이어서 보낸 조회가
커밋 전 상태를 읽는다. UI의 `createConnection()` → `reload()` 흐름이 정확히 이 패턴이다.

> `httpx.ASGITransport` 기반 테스트로는 재현되지 않는다. 인프로세스 호출이라 teardown이
> 다음 요청보다 먼저 끝난다. **실서버에서만 드러나는 종류의 결함**이다.

### 결정

**쓰기 엔드포인트는 핸들러 안에서 `await session.commit()`을 명시적으로 호출한다.**
`get_db`의 teardown 커밋은 누락 대비 안전망으로 남기되 순서를 보장하지 않는다고 문서화한다.

적용 대상: `auth`(register·login·logout·change-password), `users`(7개 전부),
`connections`(test·create·delete). 조회 전용 엔드포인트는 그대로 둔다.

`tests/integration/test_api.py::test_write_is_visible_to_the_next_read`가 회귀를 막는다.

### 근거

- **트랜잭션 경계는 요청 경계와 같다.** 이 애플리케이션에서 한 요청은 하나의 논리적 작업이므로
  핸들러가 커밋 지점으로 자연스럽다.
- 서비스 계층에 커밋을 넣는 대안은 유스케이스 조합 시 트랜잭션이 쪼개진다.
  Step 3에서 수집 워커가 여러 유스케이스를 엮을 때 문제가 된다.
- 미들웨어로 처리하는 대안은 의존성 그래프상 세션 접근이 지저분해지고, 어느 요청이 쓰기인지
  판정해야 한다.

### 고려한 대안

| 대안 | 채택하지 않은 이유 |
|------|-------------------|
| teardown 커밋 유지 | 실서버에서 read-after-write가 깨진다. 재현이 어려워 진단 비용이 크다 |
| 서비스 계층에서 커밋 | 유스케이스를 조합할 때 트랜잭션이 쪼개진다 (Step 3 워커) |
| 커밋 미들웨어 | 쓰기 판정 로직이 필요하고 세션 접근이 지저분해진다 |

## D-018. Hyper-V 어댑터 조기 구현 — Step 5를 Step 2 이전에, 경로 A 포함

| 항목 | 내용 |
|------|------|
| **결정일** | 2026-08-14 |
| **상태** | 확정 (사용자 결정) |
| **관련** | D-012, `plans/05`, `plans/ROADMAP.md` §20, 마이그레이션 `0002` |

### 배경

ROADMAP은 Hyper-V 어댑터를 Step 5에 두고, 앞당기더라도 Step 3 직후를 하한으로 정했다.
또한 §20.1은 경로 B(SCVMM)만으로 시작하고, 경로 A(호스트 직접)는 SCVMM 미관리 호스트
실사(5-3) 이후에만 착수하도록 정했다.

2026-08-14 사용자가 범위 확인 질문에 **"경로 A(호스트 직접)까지 포함"하여 지금 구현**하는
것으로 결정했다. 어댑터는 Protocol만 맞추면 독립적이라 순서 제약이 약하다는 ROADMAP §20의
평가가 근거가 된다.

### 결정

1. **Step 5의 코드 구현을 Step 2(실환경 검증) 이전에 수행한다.** 공통 계층 + 경로 B + 경로 A
   전부다. 검증은 fake 기반 단위·계약 테스트로 한다 (CST-04).
2. **운영 등록 제약은 그대로 유지한다.** SCVMM 계정 준비(§4.3)·JEA 배포 전에는 해당 연결을
   등록하지 않으며, SCVMM이 관리하는 호스트를 경로 A로 중복 등록하지 않는다 (§2.1).
   UI 등록 화면이 이 경고를 표시한다.
3. **연결 등록 API의 `kind`가 필수가 되었다** (discriminated union). 기존 vCenter 등록
   페이로드도 `"kind": "vcenter"`를 보내야 한다.
4. 계획 05의 `[검증 필요]` 중 라이브러리로 확인 가능한 3건은 해소했다 (연구 노트 §11-17 등):
   pypsrp 0.9.1의 `RunspacePool(configuration_name=...)` 지원, 인증 예외 타입
   (`pypsrp.exceptions.AuthenticationError`), CredSSP/Kerberos extra 의존성. **실환경 항목
   (§11-4·5·11~15·18)은 미해소이며 Step 2 실측과 함께 확인한다.**

### 파생 변경

- `ConnectionKind`에 `hyperv-host`·`hyperv-cluster`·`scvmm` 추가 + `WinRmAuth` 신설.
  리더 팩토리에 세 경로 모두 연결했다 — 미구현 분기 없음 (Known Mistakes 5번).
- `connections` 테이블에 `protocol`·`auth_method`·`session_configuration` 추가,
  `kind` DEFAULT 제거 (마이그레이션 `0002_hyperv_connections`).
- JEA 역할 파일은 `scripts/generate_jea_role.py`가 `host_scripts.py`에서 생성한다 —
  수집 스크립트와 JEA 함수 본문의 드리프트를 막는다 (계획 05 §12-13).

### 고려한 대안

| 대안 | 채택하지 않은 이유 |
|------|-------------------|
| ROADMAP 순서 유지 (Step 2 먼저) | 사용자가 조기 구현을 결정 |
| 경로 B(SCVMM)만 먼저 구현 | 사용자가 경로 A 포함을 명시적으로 선택. 단, §20.1의 "실사 후 운영 등록" 원칙은 코드 존재와 별개로 유지 |

폴스타는 사내 인프라 모니터링·자산 시스템으로, 게스트 OS 에이전트가 수집한 서버 사실
(실제 OS·커널 버전·시리얼·NIC·조직 정보)을 사이트별 인스턴스에 보관한다.
포탈이 하이퍼바이저에서 얻지 못하는 값들이며, 특히 **게스트 도구 미설치 VM**(FR-501의
"수집 불가")을 폴스타가 대신 관측하고 있다.

2026-08-14 사용자가 폴스타 연동을 요청했고, 범위 확인 결과 **① 게스트 OS 상세 보강**과
**② 조직 메타데이터 초기값 확보** 2가지로 확정했다 (갭 분석·물리 서버 확장은 제외).

### 결정

1. **폴스타는 `HypervisorInventoryReader`에 넣지 않는다.** 하이퍼바이저가 아니며 VM을 소유하지
   않는다. `src/domain/ports.py`에 **별도 Protocol `ServerFactReader`**를 정의한다.
   `ConnectionKind`에 값을 추가하지 않는다 — 리더 팩토리에 미구현 분기를 남기지 않기 위함이다
   (Known Mistakes 5번, D-012).
2. **접근 경로는 collectorinfra의 DBHub MCP 서버(SSE) 경유다** (사용자 결정).
   폴스타 DB 자격증명과 드라이버(DB2 `ibm_db` 포함)를 MCP 서버가 관리하므로
   **포탈은 폴스타 DB 자격증명을 보관하지 않는다.**
3. **폴스타 데이터를 포탈 DB에 스냅샷으로 저장한다** (`external_servers`).
   조회 시점에 폴스타를 조인하지 않는다 — 외부 시스템 장애가 포탈 조회 장애가 되며
   "조회는 저장소 경유"(D-007) 위반이다.
4. **매칭은 규칙별로 자동 확정과 후보 제시를 나눈다.** UUID 계열(`cmm_resource.uuid` 또는 EAV
   `SerialNumber` 정규화 — 어느 쪽이 유효한지는 실환경 확인 후 확정)과 MAC은 1:1일 때만
   자동 확정, 호스트명·IP는 **후보로만** 제시하고 운영자가 확정한다. 오매칭은 CMDB 신뢰를
   통째로 깨뜨리며 사람이 발견하기 전까지 정답처럼 보인다.
   **매칭 대상은 vCenter·Hyper-V 호스트/클러스터·SCVMM 3경로의 VM 전부이며 동일 규칙을 적용한다**
   (D-003 — 유스케이스에 하이퍼바이저 분기를 두지 않는다).
5. **조회 대상 테이블을 `cmm_resource`·`core_config_prop` 2개로 고정한다.** 폴스타 DB에는
   성능 통계(`cmm_metric_stat_h/d/m`), 알람(`cmm_alarm`·`cmm_alarm_active`·`cmm_alarm_def`·
   `cmm_alarm_log`·`cmm_alarm_def_noti*`), 계정·ACL(`acc_role`·`acc_user_group`·
   `acc_acl_resource_manager_type`), 레거시 lookup(`cmm_vendor`·`cmm_os`·`cmm_os_param`) 등
   **더 많은 테이블이 있다.** 이 중
   - 성능·알람은 `spec.md` §1.2의 명시적 비목표라 수집하지 않는다,
   - 레거시 lookup은 값이 EAV와 불일치할 수 있어 조회하지 않는다 (collectorinfra D-028),
   - `acc_*`는 담당자 메타데이터 제안에 쓸 수 있으나 **구조가 확인되지 않았다.** 착수 시
     `get_table_schema`로 확인한 뒤 9-B에서만, 제안값 표시 용도로 조건부 사용한다.

   조회 테이블 고정은 단위 테스트로 강제한다 (계획 14 §14).
   **폴스타 전체 테이블 목록은 착수 시 `search_objects`로 직접 확인하고 계획서를 갱신한다** (§2.5).
6. **착수 시점은 Step 4 이후의 신규 Step 9다** (사용자 결정). MAC·IP 수집(Step 4)이 끝나야
   매칭 키가 충분해진다. 단, 메타데이터 제안(9-B)은 `resource_metadata` 테이블이 생기는
   **Step 7 완료가 선행 조건**이다.

### 파생 변경

- `scripts/arch_check.py`에 `src.infrastructure.polestar` 등록. 특화 규칙 1(직접 import 금지)·
  2(어댑터 교차 참조 금지) 대상에 포함한다. 등록하지 않으면 검사에서 조용히 제외된다.
- 신규 테이블 4개: `external_sources`, `external_servers`, `external_server_links`,
  `external_match_candidates`. **`virtual_machines`에는 컬럼을 추가하지 않는다** —
  수집 경로와 보강 경로가 섞이면 재수집이 보강값을 덮어쓴다 (FR-602).
- VM 상세 응답에 `external.polestar` 블록 추가. `status`를 `linked`/`candidate`/`unmatched`/
  `not_configured` 4값으로 구분한다 ("값 없음 vs 수집 불가" 원칙의 연장).
- `spec.md`에 외부 시스템 **인바운드** 연동 요건이 없다. FR-11xx는 포탈이 데이터를 제공하는
  아웃바운드 API다. 이 연동은 신규 요건이며 spec 개정이 필요하다 (§미해결).

### 고려한 대안

| 대안 | 채택하지 않은 이유 |
|------|-------------------|
| `ConnectionKind`에 `polestar` 추가 | `VirtualMachine.connection_id`가 하이퍼바이저 연결을 가리키므로 VM 소속이 모호해지고 `AccessScope`(연결 단위 권한)가 무너진다 |
| 폴스타 DB 직접 조회 (asyncpg / ibm_db) | 사용자가 MCP 경유를 선택. 포탈이 DB 자격증명과 DB2 드라이버(clidriver 설치)를 떠안지 않는 이점이 있다. 대신 MCP 서버 가용성에 동기화가 종속된다 |
| 조회 시점 실시간 조인 | D-007 위반. 외부 장애가 포탈 화면 장애가 된다 |
| 호스트명·IP까지 자동 확정 | 클론 VM·DHCP·VLAN 중복으로 오매칭이 조용히 쌓인다 |
| Step 2와 병행 착수 | MAC·IP가 없어 매칭 키가 hostname·시리얼뿐이다. 사용자가 Step 4 이후를 선택 |

### 미해결

- `spec.md`에 인바운드 연동 요건(FR-13xx 가칭) 추가 여부 — 사용자 확정 필요
- 계획 14 §15의 확인 항목 9건 (MCP 도달성, 인스턴스 목록, 시리얼 포맷 등)
