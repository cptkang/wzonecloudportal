# 11. 웹 UI — Claude Design 기반 디자인 및 구현

> Wave: 0 (디자인) · 4 (구현)
> 계층: interface (`static/`)
> 담당 요건: FR-12xx(웹 UI), FR-9xx(대시보드), FR-101~118 화면, FR-401~409, FR-501·502, NFR-401~407
> 의존: 08 (구현 시) · 관련 결정: D-005, D-007, D-009

## 1. 목적

**웹 브라우저로 접속하는 포탈 화면을 통해 서비스를 제공한다** (FR-1201).

화면 디자인은 **Claude Design**으로 수행하고, **Claude Code 핸드오프**로 이 저장소에 구현한다 (D-009).

**핵심 원칙 (NFR-401)**: 자원 목록은 하이퍼바이저 종류와 무관하게 **동일한 화면·용어**로 표시한다.

## 2. 두 단계 구성

| 단계 | Wave | 도구 | 산출물 |
|---|---|---|---|
| **Part A. 디자인** | 0 | Claude Design (Claude Desktop 사이드바 또는 claude.ai/design) | 핸드오프 번들, `docs/03_design_system.md` |
| **Part B. 구현** | 4 | Claude Code (로컬 에이전트) | `static/` |

**Part A를 Wave 0에 두는 이유** (`spec.md` §6): 시안은 백엔드와 병렬 진행할 수 있고,
확정되어야 API 응답 형태(목록에 어떤 필드를 노출할지)를 정확히 정할 수 있다.

# Part A. Claude Design 기반 디자인 (Wave 0)

## 3. 전제 조건

| 항목 | 내용 | 확인 |
|---|---|---|
| 접근 경로 | **Claude Desktop 사이드바(팔레트 아이콘)** 또는 웹 `claude.ai/design` | 모바일 미지원 |
| 플랜 | Pro / Max / Team / Enterprise (베타) | 무료 플랜 불가 |
| Enterprise 사용 시 | **기본 비활성 — 관리자가 조직 설정에서 활성화** | 착수 전 확인 필요 |
| 핸드오프 대상 | 로컬 Claude Code (이 저장소) 또는 Claude Code Web | 로컬 사용 |

> **착수 전 확인**: 플랜과 Enterprise 활성화 여부를 먼저 확인한다.
> 사용할 수 없으면 §9의 대체 경로로 전환한다.

## 4. 전체 흐름

```
① 컨텍스트 주입     프로젝트 제약을 프롬프트로 명시 (§5) ← 가장 중요
        ↓
② 화면 디자인       Claude Design 캔버스에서 화면별 생성·수정
        ↓            (자연어 대화 / 인라인 코멘트 / 직접 편집)
③ 검토              내부 URL 공유(보기·코멘트·편집 권한) → 운영팀 피드백
        ↓
④ 핸드오프          Export → Handoff to Claude Code → 로컬 에이전트
        ↓            (컴포넌트 구조 spec + 실제 사용 토큰 + 레이아웃 계층 + 에셋)
⑤ 디자인 시스템 고정  번들의 토큰을 docs/03_design_system.md에 기록
        ↓
⑥ 구현 (Part B)     핸드오프 번들 기반으로 static/ 구현
```

**④가 이 방식의 핵심이다.** 스크린샷이나 Figma URL이 아니라 **Claude Code가 직접 읽는 구조화된 spec**이
넘어오므로, "기존 작업을 이어받아" 구현한다. PNG를 보고 재구성하는 손실이 없다.

## 5. 컨텍스트 주입 — 이 계획에서 가장 중요한 단계

Claude Design은 범용 디자인 도구다. **"가상 머신 관리 대시보드"라고만 말하면
전원 버튼·삭제 버튼·스냅샷 조작 UI를 자연스럽게 넣는다.** 이 포탈은 읽기 전용이므로(FR-1206, D-005)
그런 요소가 들어가면 안 된다.

또한 이 프로젝트 고유의 표시 규칙(FR-1204 "수집 불가" 3분기)은 일반적인 디자인 관행이 아니므로
명시하지 않으면 반영되지 않는다.

### 5.1 최초 프롬프트 규격

아래를 **첫 프롬프트에 포함**한다. 화면마다 반복하지 말고 캔버스 컨텍스트로 유지한다.

```
[제품]
다수의 VMware vCenter와 Hyper-V에 흩어진 가상자원을 한곳에서 조회하는
읽기 전용 인벤토리 포탈입니다. 운영자가 브라우저로 접속해 사용합니다.

[절대 넣지 말 것 — 가장 중요]
이 포탈은 자원을 조회만 합니다. 다음 UI 요소를 어떤 화면에도 넣지 마세요.
- VM 전원 켜기/끄기/재시작 버튼
- VM 생성·삭제·복제 버튼
- 스냅샷 생성·삭제·복원 버튼
- 리소스 변경(CPU·메모리 조정) 컨트롤
- 마이그레이션 실행 버튼
자원 상세 화면에도 "삭제"가 없습니다. 삭제는 하이퍼바이저 "연결" 설정에만 있습니다.

[반드시 구분해서 표시할 것]
IP 주소와 게스트 OS는 VM에 게스트 도구가 설치·동작 중일 때만 수집됩니다.
따라서 세 가지 상태를 시각적으로 구분해야 합니다.
1. 수집된 값        →  10.0.1.15            (일반 텍스트)
2. 수집 불가        →  "수집 불가 — 게스트 도구 미설치" (주의색 + 아이콘)
                       가능하면 "마지막 확인: 10.0.3.42 (3일 전)" 병기
3. 하이퍼바이저 미지원 →  "해당 없음"          (흐린 회색)
4. 실제로 빈 값     →  "—"                  (흐린 회색)
빈칸으로 두면 "IP가 없는 VM"으로 오해됩니다. 이 구분이 이 제품의 신뢰도를 결정합니다.

[통합 표현 원칙]
vCenter 자원과 Hyper-V 자원을 같은 표에 같은 컬럼으로 표시합니다.
하이퍼바이저 종류는 작은 배지·아이콘으로만 구분하고 컬럼 구성을 바꾸지 않습니다.

[접근성]
색상만으로 상태를 전달하지 않습니다. 아이콘과 텍스트를 함께 씁니다.
라이트/다크 두 테마를 모두 지원합니다.

[언어] 한국어 UI. 날짜·숫자는 한국 로케일 형식.
```

### 5.2 목 데이터 규격

**경계 사례를 반드시 포함시킨다.** 이상적인 데이터만 있으면 시안이 실제 환경에서 무너진다.

```
[목록에 포함할 데이터 — 최소 30행, 아래 사례를 반드시 섞을 것]
· 정상 VM (IP·OS 모두 수집됨)
· 게스트 도구 미설치 VM (IP·OS 없음)  ← 최소 5행. 목록에서 눈에 띄는지 확인용
· 게스트 도구 미동작 + 마지막 알려진 IP 보유 VM
· 이름이 45자 이상인 VM (예: prd-seoul-payment-gateway-app-server-node-014)
· 미발견 상태 VM (12일째 수집 안 됨 — 배지 표시)
· Hyper-V 자원과 vCenter 자원을 섞어서
· IP가 3개인 VM (다중 NIC)
· 소유자 메타데이터가 비어 있는 VM

[금지] 실제 서버명·IP·도메인을 쓰지 마세요. 캔버스는 내부 URL로 공유됩니다.
```

### 5.3 디자인 시스템 임포트

Claude Design은 온보딩 시 기존 코드베이스·디자인 파일을 인제스트하여 색상·타이포그래피·컴포넌트를 적용할 수 있다.

| 시점 | 임포트 대상 | 비고 |
|---|---|---|
| **최초 (Wave 0)** | 없음 — 신규 프로젝트라 기존 자산이 없다 | 조직 표준 디자인 가이드가 있다면 그것을 제공 |
| 이후 수정 (Wave 4 이후) | `static/` 코드베이스 연결 | 구현된 토큰과 어긋나지 않게 |

**최초에는 자산이 없으므로 첫 화면(자원 목록)에서 나온 토큰이 사실상 기준이 된다.**
그래서 §6의 순서가 중요하다.

> **주의**: 대규모 코드베이스 연결 시 지연이 보고된다. `static/`만 연결하고 `src/`는 연결하지 않는다.

## 6. 화면 디자인 순서

| 순서 | 화면 | 확정되는 것 | 요건 |
|---|---|---|---|
| **1** | **자원 목록** | **색상 토큰, 상태 배지, 표 밀도, 타이포그래피** | FR-401·405·406·1203·1204 |
| 2 | 자원 상세 | 섹션 구분, 정보 밀도, 라벨 스타일 | FR-402·409·705 |
| 3 | 대시보드 | 위젯 배치, 차트 색상 | FR-901~905 |
| 4 | 연결 관리 | 폼 레이아웃, 유형별 분기, 확인 다이얼로그 | FR-101~118 |
| 5 | 검색 결과 | 결과 카드, 수명주기 구분 | FR-403·404 |

**1번을 먼저 확정한다.** 가장 많이 쓰는 화면이고, 여기서 정해진 색상·배지·타이포그래피가
나머지 화면의 기준이 된다. 목록을 대충 넘기고 대시보드부터 만들면 나중에 전부 다시 맞춰야 한다.

### 6.1 화면 1에서 반드시 검증할 것

```
□ "수집 불가" 5행이 정상 27행 사이에서 눈에 띄는가
   → 한 행만 보면 항상 구분된다. 30행 전체를 보고 판단할 것
□ 45자 이름에서 컬럼이 깨지지 않는가 (말줄임? 줄바꿈? 툴팁?)
□ 미발견 배지와 수집 불가 아이콘이 한 행에 같이 있을 때 읽히는가
□ 다크 모드에서 주의색·회색의 대비가 충분한가
□ 하이퍼바이저 배지가 컬럼 정렬을 흐트러뜨리지 않는가
□ 전원 버튼 같은 조작 요소가 들어가지 않았는가  ← 매 화면 확인
```

마지막 항목은 **모든 화면에서 확인**한다. 대화를 이어가다 보면 Claude Design이
"관리 화면이니까" 조작 버튼을 다시 넣는 경우가 있다.

## 7. 검토

- 내부 URL로 공유한다. **보기 / 코멘트 / 편집 권한을 구분**해 부여한다
- 검토자는 캔버스에서 직접 인라인 코멘트를 남길 수 있다
- 피드백은 자연어 대화로 반영하거나, 간단한 조정은 직접 편집·슬라이더로 처리한다
- 반영 내역을 `docs/03_design_system.md`의 "결정 이력"에 누적 기록한다
- `[TODO]` 검토자(운영팀 담당자)와 라운드 횟수 확정 (`spec.md` §3.12.1)

> **리서치 프리뷰 주의**: 인라인 코멘트가 간헐적으로 사라지는 이슈가 알려져 있다.
> 중요한 피드백은 별도로 기록해 둔다.

## 8. 핸드오프

### 8.1 실행

```
Claude Design 우측 상단 [Export]
  → [Handoff to Claude Code]
      → 로컬 코딩 에이전트 (이 저장소 E:\GitHub\wzonecloudportal)
```

번들 구성:

| 항목 | 내용 |
|---|---|
| 컴포넌트 구조 | machine-readable spec |
| **디자인 토큰** | **캔버스에서 실제 사용된 값** (문서에 옮겨 적은 값이 아님) |
| 레이아웃 계층 | 구조와 관계 |
| 참조 에셋 | 아이콘 등 |

### 8.2 다른 내보내기 옵션

| 옵션 | 언제 쓰나 |
|---|---|
| **Handoff to Claude Code** | **기본 경로.** 구현으로 직행 |
| Standalone HTML | 시안을 그대로 어딘가에 호스팅해 보여줄 때 |
| `.zip` | 원시 에셋이 필요할 때 |
| PDF / PPTX | 보고용 |
| Vercel / Canva / Adobe / Gamma | 이 프로젝트에서는 불필요 |

### 8.3 핸드오프 직후 필수 검토 — 자동으로 넘어오지 않는 것

번들은 디자인 규격이지 이 프로젝트의 제약을 담지 않는다. **구현 착수 전 확인한다.**

```
□ 조작 UI 요소가 spec에 포함되지 않았는가 (FR-1206)
   전원/삭제/스냅샷/리소스변경/마이그레이션 관련 컴포넌트
□ "수집 불가 / 해당 없음 / 빈 값" 3분기가 컴포넌트 규격에 반영되었는가 (FR-1204)
□ 상태 색상이 아이콘·텍스트와 함께 정의되었는가 (FR-1211)
□ 목록이 서버 페이징 전제로 설계되었는가 (FR-1205)
   무한 스크롤이나 전체 로드 전제면 조정 필요
□ 목 데이터에 실제 서버명·IP가 섞이지 않았는가
```

**하나라도 어긋나면 구현 전에 캔버스에서 수정하고 다시 핸드오프한다.** 구현 후 고치면 비용이 커진다.

## 9. 디자인 시스템 문서 (`docs/03_design_system.md`)

핸드오프 번들은 **일회성 전달물**이다. 구현 이후의 유지보수·신규 화면 추가에서 참조할
**단일 출처**가 필요하므로, 번들의 토큰을 문서로 고정한다.

```markdown
# 03. 디자인 시스템

> 출처: Claude Design 핸드오프 번들 (YYYY-MM-DD)
> 캔버스 URL: <내부 공유 URL>

## 1. 디자인 토큰  (번들에서 추출한 실제 값)
### 1.1 색상
| 토큰 | 라이트 | 다크 | 용도 |
|---|---|---|---|
| --color-text        | | | 본문 |
| --color-text-muted  | | | 빈 값(—), 해당 없음 |
| --color-warning     | | | 수집 불가, 신선도 경고 |
| --color-danger      | | | 자격증명 오류, 연결 실패 |
| --color-success     | | | 정상 |
| --color-surface     | | | 카드·표 배경 |
| --color-border      | | | 구분선 |

### 1.2 타이포그래피 / 1.3 간격 / 1.4 radius·elevation

## 2. 상태 표현 규칙 (FR-1204·1208)
| 상태 | 색상 토큰 | 아이콘 | 텍스트 |
|---|---|---|---|
| 수집됨              | text       | 없음 | 값 그대로 |
| 수집 불가           | warning    | ⚠   | "수집 불가 — 사유" |
| 하이퍼바이저 미지원  | text-muted | 없음 | "해당 없음" |
| 값 없음             | text-muted | 없음 | "—" |

## 3. 컴포넌트 규격
데이터 테이블 / 상태 배지 / 배너 / 필터 바 / 확인 다이얼로그 / 빈 상태 / 로딩

## 4. 프로젝트 제약 (핸드오프 번들에 없는 것 — §8.3 검토 결과)
- 조작 UI 요소 미포함 확인
- 서버 페이징 전제

## 5. 결정 이력
| 날짜 | 결정 | 근거 |
```

## 10. 대체 경로 — Claude Design을 쓸 수 없을 때

플랜 미보유, Enterprise 미활성화, 토큰 예산 부족 시.

| 항목 | 대체 |
|---|---|
| 디자인 도구 | **`artifact-design` 스킬 + Claude Artifacts**로 HTML 시안 직접 작성 |
| 공유 | Artifact URL (기본 비공개, 공유 선택 가능) |
| 토큰 전달 | **수기로 `docs/03_design_system.md` 작성** — 자동 추출이 없다 |
| 장점 | 추가 플랜 불필요, Artifact CSP 제약으로 인라인 CSS/JS가 강제되어 `static/` 이관이 쉬움 |
| 단점 | 캔버스 편집·인라인 코멘트 없음, 토큰 수기 정리 필요 |

**§5의 컨텍스트 주입과 §6.1 검증 항목은 대체 경로에서도 동일하게 적용한다.**
도구가 바뀌어도 "조작 UI 금지"와 "수집 불가 3분기"는 이 프로젝트의 제약이다.

## 11. 비용·일정 고려

- **토큰 소비가 크다.** 한 디자인 세션이 Pro 주간 할당량의 50% 이상을 소비한 사례가 보고된다

- 1번(자원 목록)에 가장 많은 라운드를 쓰고, 나머지는 확정된 토큰을 재사용하므로 빠르게 진행된다

  픽셀 단위 조정은 구현 단계에서 처리한다

### 14.2 "수집 불가" 표시 (FR-501·1204) — 가장 중요한 UI 규칙

```javascript
// static/js/format.js
const UNAVAILABLE_LABELS = {
  tools_not_installed: "게스트 도구 미설치",
  tools_not_running:   "게스트 도구 미동작",
  unknown:             "확인 필요",
};

/**
 * 게스트 파생 값(IP·OS·호스트명)의 표시를 결정한다.
 * 빈 값과 수집 불가를 구분하지 않으면 인벤토리 신뢰도가 무너진다.
 */
export function renderGuestValue(guest, field) {
  if (guest.is_collected) {
    const v = guest[field];
    return v ? { text: v, level: "normal" } : { text: "—", level: "muted" };
  }
  const reason = UNAVAILABLE_LABELS[guest.availability] ?? "확인 불가";
  const last = guest[field];
  // 마지막으로 알려진 값을 병기한다 (계획 12 §3.4 — 도구가 멈춰도 이전 값 보존)
  if (last && guest.observed_at) {
    return {
      text: `수집 불가 — ${reason}`,
      hint: `마지막 확인: ${last} (${relativeTime(guest.observed_at)})`,
      level: "warning",
    };
  }
  return { text: `수집 불가 — ${reason}`, level: "warning" };
}

/** 하이퍼바이저가 개념 자체를 지원하지 않는 항목 (계획 03 §3.1) */
export function renderCapabilityValue(supported, value) {
  if (!supported) return { text: "해당 없음", level: "muted" };
  return value ? { text: value, level: "normal" } : { text: "—", level: "muted" };
}
```

| 상태 | 표시 | 토큰 | 아이콘 |
|---|---|---|---|
| 수집됨 | `10.0.0.5` | text | 없음 |
| 도구 미설치 | `수집 불가 — 게스트 도구 미설치` | warning | ⚠ |
| 도구 미동작 | `수집 불가 — 게스트 도구 미동작` | warning | ⚠ |
| 상태 불명 | `수집 불가 — 확인 필요` | warning | ⚠ |
| 하이퍼바이저 미지원 | `해당 없음` | text-muted | 없음 |
| 실제로 비어 있음 | `—` | text-muted | 없음 |

**색상만으로 구분하지 않는다** (FR-1211).

## 22. 주의사항

- **Claude Design은 범용 도구라 "관리 대시보드"를 만들면 조작 버튼을 넣는다.** §5.1 프롬프트로 막고,
  화면마다·핸드오프 후에 다시 확인한다 (§6.1, §8.3). 이 프로젝트에서 디자인 단계의 가장 큰 위험이다.
- **빈 값과 수집 불가를 구분하지 않으면 인벤토리 신뢰도가 무너진다** (§14.2). 일반적인 디자인 관행이 아니므로 반드시 명시해야 반영된다.
- 캔버스 목 데이터에 **실제 서버명·IP를 쓰지 않는다.** 내부 URL로 공유되며, 인벤토리 정보는 그 자체로 공격 표면 정보다 (NFR-206).
- 토큰 소비가 크므로 화면 단위로 나눠 진행한다 (§11).
- 리서치 프리뷰이므로 인라인 코멘트 유실에 대비해 중요 피드백은 별도 기록한다.
- 대규모 코드베이스 연결 시 지연이 있다. `static/`만 연결한다 (§5.3).
- 경고를 남발하면 무시된다. 연결 단위는 배너, 자원 단위만 행에 (§14.3).
- 대량 목록을 클라이언트에서 전부 로드하지 않는다.
