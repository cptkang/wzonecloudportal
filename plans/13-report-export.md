> Wave: 4

## 1. 목적

인벤토리 현황 리포트를 생성하고 Excel/CSV로 내보낸다.

**이 포탈은 정리 대상을 식별해 보고할 뿐, 정리 작업은 수행하지 않는다** (CST-01).
`docs/00_research_notes.md` §8.4: 상용 도구(VMware Aria Operations)조차 고아 디스크의 자동 삭제를 제공하지 않고
수동 검증을 요구한다. 잘못 식별된 자원을 삭제하면 복구가 불가능하기 때문이다.

## 3. R-1. 인벤토리 내보내기 (FR-801)

**현재 조회 조건 그대로** 내보낸다. 화면에서 필터링한 결과와 파일 내용이 일치해야 한다.

```python
async def export_inventory(
    scope: AccessScope, criteria: SearchCriteria, columns: list[str], fmt: ExportFormat
) -> AsyncIterator[bytes]: ...
```

### 3.1 대량 데이터 처리

수천~수만 행을 메모리에 올리면 서버가 위험하다.

- **저장소에서 스트리밍 조회**(서버 사이드 커서)하여 배치 단위로 파일에 기록
- CSV: 스트리밍 응답으로 즉시 전송
- Excel: `openpyxl`의 `write_only` 모드 사용. 임시 파일에 생성 후 전송하고 정리
- **행 수 상한**을 둔다(기본 50,000). 초과 시 경고와 함께 잘라내고, **잘렸다는 사실을 파일과 응답에 명시**한다.
  조용한 절단은 "전체를 받았다"는 오해를 만든다

### 3.2 "수집 불가" 표현 (FR-501 일관성)

화면과 동일하게 구분한다. 빈 셀로 두면 파일을 받은 사람이 "IP 없음"으로 오해한다.

| 상태 | 셀 값 |
|---|---|
| 수집됨 | `10.0.0.5` |
| 도구 미설치 | `[수집 불가: VMware Tools 미설치]` |
| 도구 미동작 | `[수집 불가: 통합 서비스 미동작]` |
| 하이퍼바이저 미지원 | `[해당 없음]` |
| 실제로 비어 있음 | (빈 셀) |

별도 컬럼(`게스트정보수집상태`)을 함께 제공하여 필터링·집계가 가능하게 한다.

### 3.3 컬럼 구성

기본 컬럼은 `spec.md` §2.2의 필수(✔) 속성. 사용자가 컬럼을 선택할 수 있다(FR-407 연계).
헤더는 한국어로 하되, 시스템 연동을 위해 **영문 키 행을 옵션**으로 제공한다.

### 3.4 감사 (NFR-206)

**내보내기는 반드시 감사 로그에 기록한다.** 인벤토리 정보(IP·호스트명·OS)는 그 자체로 공격 표면 정보이며,
대량 내보내기는 정보 유출 경로다.

기록 항목: 사용자, 시각, 조회 조건, 결과 건수, 형식, 절단 여부 (계획 10 §3.1)

## 4. R-2. 자원 현황 집계 (FR-802)

연결별·클러스터별·환경별로 VM 수, vCPU·메모리·스토리지 할당 합계를 집계한다.

```sql
-- 개념 예시. 조회 범위 필터 필수
SELECT connection_id, cluster_native_id,
       COUNT(*) AS vm_count,
       SUM(vcpu_count) AS total_vcpu,
       SUM(memory_mb) AS total_memory_mb,
       SUM(total_provisioned_bytes) AS total_provisioned
FROM virtual_machines
WHERE lifecycle = 'active' AND connection_id = ANY(:scope_connection_ids)
GROUP BY connection_id, cluster_native_id
```

- 대시보드(FR-902·903)가 같은 집계를 사용한다. **집계 로직을 한 곳에 두고 공유**한다
- Redis 캐시 TTL 5분, **범위별 캐시 키 분리** (계획 07 §7)

## 5. R-3. 스냅샷 현황 (FR-803)

`docs/00_research_notes.md` §8.3: 스냅샷 delta 파일 누적은 대표적인 공간 낭비 요인이다.

```python
async def report_stale_snapshots(scope, older_than_days: int = 30, page: Page) -> PagedResult[SnapshotRow]:
```

- 기준일(기본 30일) 초과 스냅샷 보유 VM 목록
- 컬럼: VM, 연결, 스냅샷 수, 최신 생성일, 경과일, 총 점유 용량, 소유자
- 경과일 내림차순 정렬
- **정리 기능은 제공하지 않는다.** 목록과 소유자 정보를 제공하여 담당자가 판단하게 한다

## 6. R-4. 유휴 자원 (FR-804)

`docs/00_research_notes.md` §8.1: 좀비 VM은 사용되지 않으면서 자원을 점유한다.

**판정 기준을 보수적으로 잡는다.** 잘못된 "유휴" 판정은 운영 중인 VM을 정리 대상으로 지목하는 사고를 부른다.

| 후보 유형 | 판정 |
|---|---|
| 장기 전원 오프 | `power_state = OFF`가 N일 이상 지속 (변경 이력으로 판정 — 계획 12) |
| 메타데이터 미등록 | 소유자·용도가 비어 있음 (FR-503) |
| 도구 장기 미동작 | `guest_availability`가 N일 이상 미동작 |

- 각 후보에 **판정 근거를 함께 표시**한다. 근거 없는 목록은 신뢰받지 못한다
- **"정리 대상"이 아니라 "확인 필요"로 표현**한다. 판정은 사람이 한다
- 유휴 판정 기준일은 설정 가능하게 (`[TODO]` 기본값 확정 필요, 잠정 30일)

> **성능 주의**: "N일 이상 전원 오프"는 변경 이력 조회가 필요하다. 이력 테이블이 크므로
> `virtual_machines`에 `power_state_changed_at` 컬럼을 두어 이력 조회 없이 판정하는 편이 낫다.
> 계획 06의 스키마에 추가할지 구현 시 결정한다.

## 7. R-5. 용량 현황 (FR-805)

- 데이터스토어별 총 용량 / 사용 / 여유 / **프로비저닝 용량**
- **오버커밋 비율** = 프로비저닝 합계 ÷ 총 용량. 1을 넘으면 Thin 프로비저닝 초과 할당 상태
- 사용률·오버커밋 임계 초과 항목 강조
- vCenter Datastore와 Hyper-V CSV/SMB를 **동일 포맷**으로 표시 (NFR-401)

## 8. R-6. OS 분포 (FR-806)

게스트 OS별 자원 수 집계. **지원 종료(EOL) OS 파악이 주 목적**이다.

- 도구 감지값 기준으로 집계하되, 구성값 폴백 항목은 **별도 표시** (FR-304, 정확도가 낮음)
- **수집 불가 자원 수를 반드시 함께 표시**한다. 이를 빼고 집계하면 "OS 분포 100%"처럼 보여 실제 커버리지를 오해한다
- OS 문자열 정규화가 필요하다(`Microsoft Windows Server 2019 (64-bit)` → `Windows Server 2019`).
  정규화 규칙은 `src/utils/`에 두고 원본 문자열도 함께 보관한다

## 9. R-7. 정기 발송 (FR-807, Could)

지정 주기로 리포트를 메일 발송한다.

- 스케줄러(계획 06)에 등록
- **수신자별 조회 범위를 적용**한다. 범위 밖 정보가 메일로 나가면 회수할 수 없다
- 발송도 감사 대상 (NFR-206)

## 11. 구현 순서

1. CSV 스트리밍 내보내기 → 검증: 대량 데이터에서 메모리 안정
2. Excel `write_only` 내보내기 → 검증: **`xlsx` 스킬로 출력 파일 구조 확인**
3. 수집 불가 셀 표현 → 검증: 빈 셀과 구분됨
4. 행 수 상한·절단 표시 → 검증: 상한 초과 시 명시
5. 내보내기 감사 로그 → 검증: 조건·건수 기록
6. R-2 집계 (대시보드와 공유) → 검증: 범위 필터 적용
7. R-3 스냅샷 → 검증: 기준일 필터, 정렬
8. R-4 유휴 후보 → 검증: 판정 근거 표시, 성능

## 13. 주의사항

- **조용한 절단이 가장 위험하다.** 상한에 걸려 잘린 파일을 전체 목록으로 오해하면 잘못된 의사결정으로 이어진다.
- 유휴 자원 판정은 보수적으로. "정리 대상"이라는 표현을 쓰지 않는다 (§6).
- OS 분포에서 수집 불가를 제외하고 집계하면 실제 커버리지를 과대평가하게 된다 (§8).
- 리포트는 조회 범위 적용을 빠뜨리기 쉬운 경로다 (계획 09 §9). 새 리포트를 추가할 때마다 확인한다.
- 정기 발송은 범위 밖 정보 유출 위험이 가장 큰 기능이다. 수신자 범위 적용을 반드시 검증한다.
